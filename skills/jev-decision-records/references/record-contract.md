# Decision record contract

Keep a readable Markdown explanation and exactly one fenced block tagged `decision-record` containing JSON. Paths in this block are relative to the explicit repository root, not the Markdown file. Link prose paths relative to the Markdown location. Never reference a secret file such as `.env` as evidence.

Required top-level fields:

- `id`, `goal`, `owner`, `next_trigger`: nonempty strings.
- `status`: `planned`, `running`, `complete`, or `blocked`. Complete means this record's stated work is done, not that the hypothesis was confirmed.
- `conditions`: nonempty array of strings defining comparison and limits.
- `sources`: array of `{id, path, sha256}`. Hash the actual source bytes. Empty is allowed before evidence is available.
- `claims`: array of `{id, kind, text, source_ids}`. Kind is `decision`, `hypothesis`, `measured`, `estimate`, `correction`, or `unknown`. Measured/estimate/correction need sources. For a numeric claim include the value, units, denominator and reproducible calculation in `text` or adjacent prose, citing the same source IDs.
- `costs`: array of `{role, basis, usd, source_ids}`. Basis is `actual_billing`, `api_equivalent`, `monthly_allocation`, `conservative_budget`, or `unknown`. USD is nonnegative number or `null`; `unknown` requires `null`. Numeric costs need sources. These categories are not automatically additive: subscription allocation and budget reservation must not be summed as separate provider charges.
- `unresolved`, `side_effects`: arrays of strings; empty means explicitly reviewed and none recorded.

Record current user authorization in prose with the supplied request's meaning. Do not fabricate a file source for a chat instruction. Mutable ledger/state files should be copied to an existing private run evidence directory before pinning a completed measurement, so later legitimate updates do not invalidate old records. Store exact measurement commands and their outputs there as appropriate. No invocation of this skill alone creates permission to run those commands against paid services.

For a correction, preserve the earlier claim text and add a `correction` claim identifying what changed, why, and the validating source. Source hashes establish file identity, not external provenance or scientific validity.

## Artifact-DAG evidence

Apply this section when recording the artifact-DAG work described in `docs/orchestration/D063_DAG_PLAN.md` (relative to the Jev Router repository root, including when using an installed skill copy); ordinary records retain the existing JSON contract. Put these identifiers in the linked evidence and the relevant claim or adjacent prose rather than inventing required top-level fields:

- Goal/graph revisions and run/task/attempt IDs; distinguish the task count from the worker pool and concurrent execution slots.
- Check ID/version, runner argv/cwd/environment, required input/output artifact revision vector, and the actual execution result. A registry entry or mapping count establishes coverage only. A pass needs executed assertions for those revisions; unknown, skipped, or stale evidence cannot establish completion.
- Local checks and integration checks as separate results. Record which public requirements have executable checks, which have run with normal/defective controls, and which remain unmapped. Preserve the blocked product state even if the controller's synthetic fixtures pass. Apply the predeclared completion condition across public checks and independent grading: an independent pass does not override a failed required public check. When a later public diagnostic becomes a required gate, pin the new criterion/version to its applicable runs; retain earlier results under their original gates and report the additional regression separately. Passing a fixed suite does not establish broader equal quality. Do not feed hidden grader details into planning or repair.
- Execution mode and action evidence. Distinguish a mocked answer, a proposed action, an applied plan revision, and an actual runtime attempt. Link the before/after graph revision for a semantic change and the process/attempt receipt plus bound candidate, checker, fixture, and environment revisions for execution. A handler name or returned success label alone does not establish that the action ran; local runtime execution also does not establish a live provider call or product success. An arm's label does not establish that its named stages ran.
- Repair scope and attribution. Distinguish failed assertions, unexecuted checks, identified fixture/prerequisite blockers and unresolved causes. Link affected owners to the evidence that implicates them; an unexecuted case alone does not establish a faulty owner. For a case covering multiple requirements, distinguish coverage-based owners from owners linked to the failing assertion. Bind assertion IDs to versioned check/mapping evidence and implicated artifact revisions; record explicit fallback when that evidence is unmapped or stale. Record leaf/unit/requirement expansion in candidate construction separately from selected and actually dispatched worker counts, plus the full public recheck result. For artifact-scoped repair, separate allowed writes from actual changes and pin the inherited bytes of unchanged artifacts. An offline incident replay or a fresh run needing no repair does not establish live repair success or worker-call savings.
- Causal candidate and history evidence. For a suspected producer-to-intermediate-to-consumer failure, link the path's evidence and the candidates, exclusions, read/write scopes and prior failed attempts actually supplied to the decision and worker. Distinguish a proposed path, inspected source behavior and an observed runtime branch. Declared ownership is not proof of the fault location; an upstream owner omitted by the controller was not considered and rejected by Jev. Pin repeated-failure signatures and artifact revisions rather than treating a fresh attempt ID as evidence of a different cause. For no-progress recovery, link the applicable policy and new, revision-bound evidence that permits another attempt; rearranged source ranges or changed wording/model/effort alone do not establish new evidence. Distinguish recovery assessment, callback execution and the eventual worker/provider attempt. Record any resulting scope change and outcome without claiming that widening candidates alone repaired the issue.
- Model/effort selection evidence. Separate generated recommendations, dated support documentation and CLI versions, account-specific availability observations, permitted profile catalog/question revisions, the actual typed choice, and the dispatched CLI arguments and receipt model identity. Where question IDs are only transport keys, verify that the instructions themselves name the target task, worker, artifacts and paths; different keys do not make otherwise identical question bodies task-specific. A catalog or alias is not live availability, and a successful selection is not execution. Record requested effort separately from any runtime acknowledgment; latency, token totals or accepted argv do not establish the model's internal effort. Apply the experiment's mismatch/fallback rule and preserve unknowns rather than counting an unrecorded substitution as selected-profile success. Quality gates and end-to-end efficiency remain separate outcomes, including the profile decision's own time and cost.
- Request counts and scoped limits. Separate decision callbacks, local transitions, CLI invocations and actual provider requests. For a stop before sending, record the applicable condition/shared limits, charged usage, prospective reservation and stopping arithmetic. Remaining shared budget does not negate a smaller condition cap; a prevented send is not a provider call. Distinguish a prospective reservation from actual pending/settled ledger entries. For a required transmission gate, bind each executed phase to the exact serialized request, policy/source hashes and actual reservation/send receipt. A standalone pass or dispatch-intent event does not prove enforced pre-send validation or a POST; POST0 after reservation does not mean reservation0 or settled billing.
- Input-size evidence. Distinguish serialized HTTP body bytes, formatted evidence-file bytes, and model input tokens. Measure the serialization actually sent; a formatted file's size is not the wire size. Controller-side lossless reconstruction does not establish model understanding or provider acceptance; distinguish the actual model-visible representation of failures, history and candidates from controller-only restoration metadata. Passing a body-byte bound does not establish that model context limits are satisfied. For admission, record the model/version, documented limit and counted scope, method/tokenizer/version, framing coverage and sources. Distinguish exact preflight counts, estimates, proven upper bounds and observed/billed usage; a tokenizer count is not exact for the full request unless its model/framing match is established. Historical aggregate-usage fit does not establish per-question context fit. Local admission does not guarantee provider acceptance, and a blocked send has no provider response; unobserved inference usage remains unknown. Retain observed counterexamples to admission policies; correct derived acceptance labels against attempt status and response evidence without rewriting the failed assessment.
- Failure and billing states. Keep a known HTTP failure, missing inference usage, an outstanding reservation, and a later confirmed refund separate. Link any reconciliation to the original request and saved provider/account evidence, state matching limitations, and preserve the original attempt result. A confirmed zero charge does not prove zero model input tokens or successful execution and does not authorize replay. Classify follow-ups by request/policy hashes and actual transmission history: a corrected pre-send failure, a changed diagnostic question and a retransmission are distinct attempts with their own authorization and costs.
- Limit-policy changes. Record the current user authorization, policy/schema version and before/after limits without rewriting earlier runs. Treat `null` as unlimited only where the applicable limit-field contract explicitly says so; unknown usage or cost remains unknown. Do not substitute zero, `Infinity`, or an arbitrary large limit. Preserve cumulative ledger identity, usage and settlement history across migration; lifting a spend limit does not remove provider/model limits or resolve an uncertain request.
- Shared preparation and concurrency. Pin reused preparation bytes to the original run and receipt. Separate new preparation spending from a clearly labelled attribution of historical preparation cost; do not charge reuse as another provider call. Distinguish concurrent workflows, observed worker/provider overlap and serialized ledger operations. Record ledger wait time and the cohort execution schedule when available; a simultaneous start request alone does not prove overlap, and comparisons with different cohort concurrency are not otherwise identical timing comparisons.
- Duration basis and boundary. Keep estimated critical-path time apart from measured end-to-end completion; unknown duration and failed-trial completion stay `null`. Do not count a verification span twice or call a shorter failed attempt a completion speedup. When providers emit different events, name the actual retained start/end events used for stage spans; do not invent absent start events. Preserve the earlier analysis when correcting a boundary.
- Review input. Record what each reviewer or model actually received. A numeric packet supports review of supplied aggregates; it does not establish a raw receipt/source audit, revision binding, or product grading.

The record checker validates references and hashes only; it does not enforce these semantic relationships or certify the check runner. Reinspect the referenced execution evidence for each claim.
