# D070 — n9 집중 해소와 실제 수리 실험

2026-10-11. [역할 계약](../agents/D070_PARALLEL.md)을 먼저 기록하고 분업한다. 최신 사용자 목표는 기존 Claude 단독 성공보다 완료 시간과 환산 비용을 모두 줄이는 것이다. 기존 결과는 보존한다.

현재 가설은 분해·배정 질문이 인터페이스 결합을 우선하고 큰 묶음의 예상 실행 부담·후속 대기·불균형을 충분히 표현하지 못한다는 것이다. 실제 n9 결정과 코드 경로를 확인하기 전 원인으로 확정하지 않는다. 작업 크기와 실제 의존 관계를 제공해 Jev가 더 작은 실행 가능한 묶음을 선택하도록 수정한다. 모델·effort·검사·동시성2를 먼저 고정해 비교한다.

실험 A는 새 분해 정책으로 처음부터 Jev 전체 판단·Claude 구현·필요한 공개 수리·독립 채점까지 실행한다. 실험 B는 보존 D068 실패 후보의 새 사본에서 현재 공개 실패 근거를 만들고, 새 Jev 수리 선택을 실제 선택 worker와 연결해 상속·공개 재검사·독립 채점까지 검증한다. A/B는 별도 비용·시간으로 기록하며 병렬 실행의 경합도 보존한다. B의 짧은 수리 시간을 처음부터 개발한 Claude 기준선과 비교하지 않는다.

완료는 공개85/85와 독립63/63, 생략0을 모두 요구한다. 비용은 동결 공식 단가 환산과 실제 월 정액 청구 미상을 구분한다. 토큰은 입력·출력·캐시생성·캐시읽기를 분리한다. 미완료 시간을 성공 속도로 부르지 않는다. 개발 호출·진단·수리·공통 준비·모니터를 각각 남긴다.

기존 D069 성공은2364670.661541ms/5809782tokens/$12.3604662, D067 Claude 성공은2180703.603375ms/6772666tokens/$21.1351716이다. 조건당1회·과거코호트차이 때문에 새 한 번의 우위를 인과효과나 일반 성능으로 확대하지 않는다. 구체적 새 정책/manifest·모델 입력 검사는 분석 후 실행 전에 여기에 추가한다.

기존 누적 장부의 무상한 정책과 ID·이력을 유지한다. 기본 요청256kB 및 모델 문맥64k/32k, 수리 입력24,000B 운영 상한, 불확실결과 중단 규칙을 지킨다. 정확 tokenizer는 확인되지 않았으며 바이트 추정을 실제 모델 토큰으로 취급하지 않는다. 실제 모델GET·인증·고정Docker환경과 회귀/원시검토를 통과한 뒤 root가 유료 실행한다. 현재 새 실제 실행은 미착수다.

## 실행 전 고정 정책

원시 추적에서 기존 분할은21→`18·1·1·1`→`15·1·1·1`→`12·1·1·1`이었다. n9의 마지막keep은 깊이3에서 split 선택지를 제거한 controller의 단일 선택이며 새 Jev 응답이 아니다. n9는 전체21unit중12개,80요구중50개,22artifact중13개를 소유했다. 의존성은 없지만 실행 시작379,411.948ms 뒤에 여섯 번째로 시작했다. [원시 분석](../../benchmark-runs/d070-baseline-analysis-01/analysis.json)과 [독립 검토](../../benchmark-runs/d070-review/n9-stop-review-01.json)를 보존한다.

A는 `d070-adaptive.json`의v6 `balanced-v2`만 활성화한다. 네 묶음은 부담 기준의 분모이며 실제 leaf 개수를 미리 정하지 않는다. 동일catalog의 terminal 부담 상한은unit6/요구20/artifact6/path10이며, 각각 `max(ceil(total/4), largest_atomic_unit)`이다. 부담을 넘는 복수unit 묶음에는keep을 제시하지 않는다. Jev가 고른split 수에 따라 각 자식의unit수는 `ceil(parent_units/children)` 이내로 배정한다. 원자unit은 쪼개지 않는다. 깊이3에서도 큰 복수unit이 남으면 추가 분해를 허용하되 기존 최대30leaf/59node/435관계쌍/128provider call은 유지한다. 실제 분할 수·멤버십·관계는 Jev 선택과 별도 controller 제약으로 구분해 기록한다.

인터페이스 언급은 coupling 힌트이며 검증된 의존 관계로 간주하지 않는다. 순환 관계는 기존 원자적검사에서 거부한다. ready task 실행 순서는 이번 조건에서 바꾸지 않는다. 두 실행 슬롯, 동일Opus5.5 medium, 두 수리 라운드, 원래검사와 worker권한을 고정한다. 새 정책의 모듈·계약·manifest 해시를 실행 전에 동결한다.

B는 `d070-preserved-repair.json`의v5 수리 정책을 사용한다. D068최종 후보를 새 디렉터리로 복사해 현재 공개 실패를 재현하고, Jev가 고른 수리만 새 Claude 호출로 실행한다. 초기 복사는 provider 구현 호출0으로 별도 기록한다. 선택하지 않은 산출물의 bytes/mode/revision 보존과 전체 재검사를 확인한다. 기존 실패 후보의 생성비용을 B의 새 비용에 다시 청구하거나 B의 수리 시간을 처음부터 개발한 A/Claude의 완료 시간으로 비교하지 않는다.

판정 기준은 공개85/85·독립63/63·생략0을 만족한 새 A의 runner wall과 공식 API 환산 비용이 과거 Claude 단독 각각2,180,703.603375ms와$21.1351716보다 모두 낮은가이다. 독립 채점시간/runner→채점종료 실시간/대기간격은 별도 보고한다. 조건당1회이며 과거 Claude는4조건 동시, 이번 A/B는 서로 다른 개발·수리가 겹친다. 이 차이 때문에 측정된 우위가 있더라도 Jev의 일반적 인과효과라고 단정하지 않는다.

## 사전 검사에서 확인한 결함

첫 preview는 전체wire최대127,891B를 확인했지만 질문별 한도를 검사하지 않았다. Root의 `planning-admission-02.json`에서 원자21leaf 경로의 질문당 추정32,116이32,000 운영 한도를 넘었다. 이 경로는 wire123,991B로 전체 최대보다 작았다. 따라서 전체byte최대만 검사하는 검증은 충분하지 않았다. 실제POST는0이며 최초 preview와 admission 결과를 보존한다. 질문당 최대와 전체 최대를 별도로 검사하고, balanced-v2 관계 상태의 중복만 제거한 뒤 다시 동결한다.

수리 실행기 초안에는 알려진 HTTP실패 뒤 deadline 확인이 원래 실패 원인을 덮을 수 있는 경로가 있었다. 검토에서 발견해 `preservedRepairTerminalState`로 수정하고 반례로 검증했다. 검토한 변경은 아직 실제 수리 성공을 의미하지 않는다. 새 측정 helper의 `null < baseline` 비교와 중복 시작 event 대응 결함도 집중 반례로 수정했으며 첫 분석 파일은 보존했다.

최종 관계 상태는 `state.units`의 원문을 보존하고, `leaves[].interfaces`가 해당 `unit_ids`로 정확히 복원되는지 검사한 뒤 중복만 제거한다. 모델 입력에 복원 규칙을 명시한다. `d070-decomposition-preview-02`의15개 대표 최대 요청을 실제v2 admission 경로로 검사한 `planning-admission-03.json`은15/15허용이다. 최대wire114,854B, 전체입력추정46,454/64,000, 질문당추정26,958/32,000이다. 이 값은 휴리스틱이며 실제 모델 토큰·수락 보장이 아니다. 이전거부 기록01/02를 지우지 않았다.
