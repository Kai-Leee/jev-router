## 입력 한도 사전 확인과 실제 반증

[모델 정책 v1](contracts/jev-token-admission.v1.json)의 근거는 [Jev 문서](https://jev-ai.pro/docs), [TypeSafe 모델 문서](https://docs.typesafe.ai/models)와 SDK다. 공식 표기는 요청 전체64k, state+가장 긴 질문32k다. 구현의 64,000/32,000은 로컬 십진 해석이며 exact tokenizer·공급자 framing을 확인한 값이 아니다. HTTP body 256,000B·질문 수64와 모델 문맥 제한도 구분한다.

v1은 과거 요청 replay에서 맞았지만 새 실제 요청을 잘못 허용했다. 이 반증을 보존하고 v2를 별도 정책으로 만들었다. [v2 정책](contracts/jev-token-admission.v2.json)은 trusted stage·요청/정책 SHA를 검증하고 budget 예약 전 repair 전송량을 24,000B로 제한한다. 초과 입력은 자르거나 재전송하지 않고 로컬 차단한다. 현재 v2 요청의 여유는 285B이며 앞으로의 입력에도 수락을 보장하지 않는다.

수리 wire는 D068 대비 **73,356B 감소(−75.5694%, 분모 97,071B)**, v1 대비 **46,795B 감소(−66.3665%, 분모 70,510B)**했다. 이는 바이트 감소다. 실패 응답에 토큰 사용량이 없어 전후 모델 입력 토큰 감소율은 측정할 수 없다.

진단03의 Jev 선택은 `repair_repair-failure-owners`였다. 전송된 질문과 답은 [진단03](../../benchmark-runs/d069-admission-probe-03/result.json), 입력은 [v2 packet](../../benchmark-runs/d069-packet-v2-01/result.json)에 연결된다. 이 호출은 **정확히 그 요청의 수락과 선택**을 입증하며 실제 작업자 실행으로 연결한 진단은 아니다.

## 담당 연결과 수리 범위

현재 안정 assertion 4개를 지원하며 전수 assertion mapping은 아니다. 원시 check·assertion 계약 hash, 실제 plan·환경·artifact revision·evidence key가 맞는 경우에만 `assertion → 공개 인터페이스 산출물 → 현재 담당 task`를 연결한다. 미지원 근거에는 기존 task 전체 산출물 fallback을 남겼다. 인터페이스 담당은 원인 파일 확정과 다르다.

보존 D068 후보를 새 runtime에서 검사하면 **84/85**, 동일 `existing-output-refused` 실패, 후속 assertion3개는 `not_reached`다. D068 case 단위 후보는 담당3명/consumer포함4명이었지만 새 assertion 근거는 **A03 담당 n9 한 명**, 또는 **A03+A21 담당 n9+n3 두 명**으로 좁혔다. 이는 후보 범위 변화이며 실제 재호출 절감이 아니다.

v2는 선택 요구사항·산출물 인터페이스·실패와 미도달 상태·공개85개 case를 모델 입력에 보존한다. 반복 키는 tables로 표현하고 controller provenance는 SHA 참조로 옮긴다. 모델이 참조 파일을 열 수 있다고 가정하지 않는다. 14개 의존 인터페이스 상세는 필요한 실제 worker packet에 남는다. owner-only worker packet은 **17,834B**, consumer 옵션은 **17,820B와 29,616B**다. Jev wire 24,000B 상한은 Claude worker 입력 상한이 아니다.

실행기는 선택된 산출물 경로만 쓰도록 제한하고 나머지 바이트·mode·revision을 검증해 상속한다. 이미 검증된 비선택 task는 provider 없이 carry-forward하고 공개 검사는 다시 수행한다. 이 경로는 오프라인·통합 검증을 통과했으나 fresh D069의 실제 수리·상속은 **0회**이므로 live 효과는 미측정이다.

## 시간이 늘어난 구간

[D068/D069 계획 대조](../../benchmark-runs/d069-preflight/plan-equivalence.json): 각 planning.json은 **186,971B**, SHA `46d88084c6c77a6d4b2e5c9fff7e55bde5254e6777074c25fbf7f449f0c2d7d3`로 동일하다. 계획 재사용으로 POST를 생략한 것은 아니다. 새 Jev47개 POST와 응답을 모두 남겼다.

- Jev HTTP 합 **40,708ms**. GET·장부 처리 등을 포함한 Jev adapter 합 **74,291.823706ms**, 계획 전체 **76,135.268792ms**와 구분한다.
- 큰 leaf n9는 **산출물13개·쓰기 경로16개·요구사항50개**를 맡았다. D068 **769,663.212292ms/$3.1683042** → D069 **1,328,417.012167ms/$5.3706916**로 **558,753.799875ms** 늘었다. 해당 원시 영수증은 [claude-0053](../../benchmark-runs/d069-comparison-01/jev_all/receipts/claude-0053.json)이다.
- 후속 n3는 n9의13개와 A20·A22를 포함한 입력 산출물15개를 기다린다. 이번 n3 구현은 **460,845.702166ms**, 이전514,228.51525ms보다 짧았다. n9 집중과 후속 의존 때문에 동시 2슬롯이 전체 시간을 그대로 절반으로 줄이지 않는다.
- n7/n3 내부의 허용 밖 read 시도는 각3회 거절됐다. 작업자 범위를 늘려 우회하지 않았고 두 호출 모두 정상 종료했다. 이를 최종 제품 실패나 별도 수리 호출로 세지 않는다.

관측한 큰 증가 구간은 n9 구현이다. 같은 분할에서도 생성·추론량과 캐시 사용이 달라졌다. 특정 프롬프트나 수리 코드가 증가를 일으켰다는 인과 결론은 내리지 않는다. 반복 측정·큰 leaf 분할 정책 검토·실제 실패 fixture에 대한 수리 실행은 다음 별도 실험 후보이며 이번 결과에 추가 실행을 섞지 않았다.

- 모니터는 질문 범위 추정9,972와 공급자 요청 전체 입력10,891을 비교해 9.2% 오차를 주장했다. **서로 다른 범위라 그 비율과 이를 이용한 보정 제안은 기각했다.** 요청 전체의 로컬 추정은9,998이며 exact model count가 아니다. [원문](../../benchmark-runs/d069-monitor-01/result.json)과 [root 정정](../../benchmark-runs/d069-preflight/monitor-review-02.json)을 함께 보존하고 자동 추가 호출을 하지 않았다.
- root 초안은 arm→채점 종료 2,425,888ms를 cohort 구간으로 잘못 표기했고 모니터 packet의 n3 입력 수를14개로 보냈다. 원시 감사에서 각각 arm 구간·15개로 정정했다. 실제 수리 packet의 상세 의존 인터페이스14개와 full plan의 입력15개는 다른 범위다. 원시 분석 산식은 바뀌지 않았으며 정정02에 두 오류를 보존했다.
- 첫 종료 Docker snapshot은 도구의 절단된 화면 출력을 복사해 JSON이 깨졌다. 해당 실패 파일을 보존하고 stdout을 파일로 직접 저장한02만 감사에 사용했다. [전후 감사](../../benchmark-runs/d069-preflight/container-cleanup-audit-01.json).

## 분석 재현·보존·남은 일

아래 분석은 네트워크·유료 호출 없이 원시 영수증의 SHA와 합계를 확인한다. 이미 존재하는 출력은 덮어쓰지 않으므로 재현 때 새 출력명을 쓴다.

```sh
node benchmark-runs/d069-analysis-tools/analyze.mjs \
  --run benchmark-runs/d069-comparison-01 \
  --preserved-recheck benchmark-runs/d069-preserved-recheck-01 \
  --admission-probe benchmark-runs/d069-admission-probe-01 \
  --admission-probe benchmark-runs/d069-admission-probe-02 \
  --admission-probe benchmark-runs/d069-admission-probe-03 \
  --monitor benchmark-runs/d069-monitor-01 \
  --output benchmark-runs/NEW_D069_ANALYSIS.json
```

분석02는 입력 근거970개를 고정한다. 원시 감사에서 실행 소스 **247/247**, 과거 파일 **4,482/4,482**의 변경0을 확인했다. 새 arm 장부 변화는 입력 **13,005,287→13,902,686(+897,399)**, 정산 **668→715(+47)**이며 pending/blocked null·기존ID·한도null을 유지한다.

남은 일은 실제 실패 후 산출물 수리→선택 worker→상속→공개 재검사를 끝까지 실행한 증거, 반복 조건의 완료시간 분산, 미지원 assertion mapping, 정확한 모델 tokenizer/framing이다. 현재 성공 조건에서 없던 수리를 성공했다고 표시하거나 실패를 주입해 이번 완료 영수증을 바꾸지 않는다.

부수 효과: 소스·문서·후보·원시 요청/답·실패 로그·진단 사본은 로컬 미커밋으로 남겼다. benchmark 모델 호출과 독립 grader·모니터는 종료했다. 실험 컨테이너는 제거됐고 기존 **22개/실행3개**의 ID·상태는 그대로다. 새 commit/push·전역 스킬 설치·Personal OS/Vault 변경은 하지 않았다.

종료 검증: [문서·근거 감사01](../../benchmark-runs/d069-preflight/closeout-validation-01.json)은 분석 근거970개·launch247개·문서11개·로컬링크90개에 대해 실패0이다. 구조화 결정 기록21sources/16claims와 `git diff --check`도 통과했다. 이 검사는 새로운 모델 호출 없이 파일 hash·합계·경로를 확인한다.
