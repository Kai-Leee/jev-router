# 공식 자료 조사와 검증 설계

확인일: 2026-10-10 (Asia/Seoul). 방법: 공식 문서의 관련 본문을 웹으로 읽고 기존 로컬 설계 문서를 대조했다.
검증 수준: **문헌·문서 확인**. 라이브러리 설치, 실제 Jev 요청, 새 스케줄러 실행, 비교 벤치마크는 하지 않았다.
외부 구현의 성과를 Jev Router의 성과로 전이하지 않는다. 아래 적용 내용은 우리의 설계 제안이다.

## 1. 조사에서 가져올 구조

| 출처·기존 방식 | 확인한 내용 | 우리 설계에 적용 | 전이 한계 |
|---|---|---|---|
| LLVM SelectionDAG | DAG를 만든 뒤 기계 제약을 고려해 실행 순서를 결정 | 의미 관계 판단과 스케줄 계산 분리 | 개발 작업의 소요·의존성은 명령어보다 불확실 |
| Python graphlib | DAG 준비 검사, ready 노드와 done 처리 | 검증된 선행 결과가 생기면 후속 해제 | 모델 배정·시간 최적화·검증 계약은 제공하지 않음 |
| Ray task / resource | 결과 참조에 따른 선행 조건, 자원에 따른 실행 제한 | artifact dependency와 실행 슬롯 분리 | 자원 선언이 실제 파일 격리를 보장하지 않음 |
| Dask scheduling | 작업 우선순위, worker 대기와 데이터 전달을 함께 고려 | 작업 수보다 전체 대기·전달·통합 시간을 평가 | 문서상의 정책과 현재 구현은 다를 수 있음 |
| Anthropic orchestrator-workers | 입력에 맞는 작업 분해·위임·결과 통합 | 준비/판단/작업자/통합 책임 계약 | Jev typed API가 자유문 계획 모델을 대체한다는 증거는 아님 |
| Anthropic agent evals | 결과 상태와 수행 기록, 코드·모델·사람 검사 구분 | 제품 성공·계획 유효성·하네스 검증을 따로 측정 | 당사 시스템의 효과를 보장하지 않음 |

## 2. 출처별 확인 범위

### R1 Jev API

출처: [Jev 공식 API 문서](https://jev-ai.pro/docs). 읽은 부분: SDK setup, question types, models and limits, errors and retries.

확인한 연결 계약: baseURL은 `https://jev-ai.pro/api`, 판단은 `POST /v1/systemone`, 기본은 `jev-latest`.
TypeSafe SDK를 사용할 때 key와 baseURL을 함께 설정하며 키는 서버 환경에 둔다.
모델 목록 GET은 추론을 실행하지 않는다. 요청은 같은 state에 대해 여러 typed question을 평가한다.
choice는 2–255개 후보, 질문은 요청당 최대 64개, JSON body는 최대 256000 bytes이며 모델 문맥 제한은 별도다.
score의 순서형 값은 작업 소요 초가 아니다.

우리 적용: 기존 client와 장부를 재사용하고 요청 목적지·실제 모델을 기록한다. 서로 앞 답에 의존하는 질문은 별도 단계로 나눈다.
422는 같은 입력으로 재시도하지 않는다. 429는 Retry-After를 존중한다. 502/503의 확인된 실패만 제한적 재시도를 검토한다.
504/연결 손실은 처리 결과를 확인하기 전 유료 POST를 반복하지 않는다.
본 조사에서는 인증 GET도 호출하지 않았다. 한도·가용성은 실제 실행 전 현재 문서를 다시 확인한다.

### R2 LLVM SelectionDAG

출처: [LLVM Code Generator — SelectionDAG Scheduling and Formation](https://llvm.org/docs/CodeGenerator.html#selectiondag-scheduling-and-formation-phase).

문서에서 DAG를 선형 명령 순서로 바꾸며 지연과 기계 제약을 고려한다고 설명한다.
우리 적용은 “관계를 정하는 단계”와 “관계에 맞게 순서를 계산하는 단계”의 분리다.
컴파일러처럼 지연이 고정되고 그래프가 완전하다고 가정하지 않는다. 프로그램 개발의 숨은 의존성은 실행 후 갱신해야 한다.

### R3 Python graphlib

출처: [TopologicalSorter](https://docs.python.org/3/library/graphlib.html).

`prepare`, `get_ready`, `done`과 순환 오류 처리를 확인했다.
우리 적용은 ready 집합을 유지하고 산출물 검증 완료 이벤트에 따라 후속을 여는 방식이다.
작업 프로세스 종료 때 바로 done을 적용하는 것은 우리 요구보다 약하므로 verification node를 두는 설계로 보완한다.
기존 프로젝트의 JavaScript 런타임을 Python으로 바꾸자는 제안은 아니다.

### R4 Ray task dependencies

출처: [Ray Tasks — Passing object refs / Waiting for Partial Results / Fault Tolerance](https://docs.ray.io/en/latest/ray-core/tasks.html).

선행 결과를 참조하는 task는 결과가 준비된 뒤 실행되고, 부분 결과 대기로 전체 완료까지 기다리지 않을 수 있다.
우리 적용은 필요한 선행 산출물만 기다리고 완료된 가지의 후속을 즉시 준비하는 방식이다.
Ray의 기본 실패 재시도를 유료 Jev/CLI 호출에 그대로 적용하면 중복 실행 위험이 있으므로 별도 실행 계약이 필요하다.
Ray 설치나 현재 runner 교체는 하지 않았다.

### R5 Ray resources

출처: [Ray Resources](https://docs.ray.io/en/latest/ray-core/scheduling/resources.html).

논리 자원으로 실행 진입을 제한하며 이 선언이 물리 자원 사용 제한과 같은 것은 아니라고 설명한다.
우리 적용은 모델/검증/파일 소유권 슬롯을 명시적으로 관리하는 것이다.
토큰 예산, 파일 격리, 모델 도구 권한은 자체 계약이 필요하다. CPU 슬롯 하나로 이 경계를 모두 해결하지 않는다.

### R6 Dask scheduling policies

출처: [Dask Scheduling Policies](https://distributed.dask.org/en/stable/scheduling-policies.html).

실행자 선택에서 대기량·데이터 전달·제약을 고려하고, 임계 경로·공정성·메모리 등 서로 경쟁하는 목적을 휴리스틱으로 다룬다.
우리 적용은 모델 응답 시간만 비교하지 않고 전달·시작·대기·통합을 포함하는 것이다.
문서 자체가 실제 소스 확인을 권하므로 특정 내부 알고리즘 버전을 재현했다고 주장하지 않는다.
이번 제안은 Dask 알고리즘 복제나 최적해 보장이 아니다.

### R7 Anthropic orchestrator-workers

출처: [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents), orchestrator-workers 절.

중앙 모델이 입력에 맞춰 하위 작업을 정하고 작업자를 위임한 뒤 결과를 통합하는 패턴을 확인했다.
우리 적용은 자유문 후보 준비를 별도 책임으로 남기고, 반복되는 구조화 선택을 Jev로 옮기는 것이다.
생성해야 할 정보가 실제로 없어졌는지와 다른 단계로 이동했는지를 따로 측정한다.

### R8 Anthropic agent evaluations

출처: [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

결과 상태와 수행 기록을 구분하고 코드·모델·사람 검사를 목적에 맞게 조합하는 접근을 확인했다.
우리 적용은 계획 생성 성공, 유효 배정, 공개 검사, 독립 제품 채점을 별도 상태로 보존하는 것이다.
한 번 성공한 실행이나 모니터의 완료 주장만으로 개선을 판정하지 않는다.

추가 탐색: HEFT 원 논문의 대학 저장소 검색 결과까지 확인했으나 본문 열람은 실패했다.
따라서 이 설계의 알고리즘을 HEFT 재현으로 부르지 않았고, 논문 수치·세부 산식을 채택하지 않았다.

## 3. 로컬 결과와 연결

읽은 자료: [D061](../D061_MAX_WORKERS.md), [D062](../D062_LIVE_PLAN.md), [현재 상태](../../agents/STATE.md),
[계약 안내](../contracts/README.md), [기존 평가 조사](../../EVALUATION_RESEARCH.md).
아래는 해당 문서가 보고한 사실과 그에 대한 설계 해석이다. 원본 실험 재실행·원시 영수증 재집계는 이번 범위가 아니다.

- 작업자 상한 확대는 독립 작업 증가나 동시성 증가와 같지 않다 → task/worker/slot을 분리한다.
- 포함/제외 질문들의 답을 모은 전체 배정이 용량을 위반했다 → 용량에 맞는 선택지를 구성하고 예약을 갱신한다.
- API 성공과 계획 성공이 달랐다 → 유효 계획률과 실제 제품 성공률을 따로 측정한다.
- 공개 검사 명세와 실제 실행 연결이 완성되지 않았다 → 실행 가능한 검사 mapping을 선행 작업으로 둔다.
- 기존 소스·실험 기록을 유지해야 한다 → 새 모드와 새 조건으로 비교하고 과거 결과를 재해석해 덮지 않는다.

관측으로 확정할 수 없는 부분: 모델의 내부 선택 이유, DAG 방식의 성공률, 순차 소유자 선택의 추가 비용을 상쇄할 병렬 이득.

## 4. 제안한 효율 개선 가설

H1. 후보 용량 검증을 앞당기면 유효하지 않은 대량 배정과 같은 질문 재호출을 줄일 수 있다.
H2. 산출물 기준 의존성을 사용하면 같은 레벨의 전체 완료를 기다리는 불필요한 barrier를 줄일 수 있다.
H3. 파일 충돌을 의미적 의존성과 분리하면 잠금 때문에 생긴 직렬화를 설명하거나 경계를 다시 설계할 수 있다.
H4. 반복 질문 생성과 메인의 중복 재판단을 줄이면 계획 시간이 감소할 수 있다.
H5. 임계 경로 주변의 유효한 분할을 우선하면 무조건 세분화하는 경우보다 전체 완료가 빨라질 수 있다.

모두 미측정 가설이다. 후보 준비·검증·통합·호출 수가 늘어 총 시간이 악화될 가능성도 같은 지표로 확인한다.

## 5. 검증과 비교 설계

### 단계 A: 모델 없는 구조 검증

실행기가 갖춰지면 다음 사례를 가짜 시계와 모의 작업자로 검증한다. 이번에는 사례와 예상값만 작성했다.

1. 단일 사슬: 선행 검증 이전에 후속이 시작하지 않아야 한다.
2. 갈라졌다 합치는 그래프: 독립 가지가 겹쳐 실행되고 합류는 필요한 양쪽 검증을 기다려야 한다.
3. 길이가 다른 가지: 짧은 가지의 후속이 무관한 긴 가지 때문에 막히지 않아야 한다.
4. 공유 파일: 의미상 독립이어도 파일 소유권이 충돌하면 같은 범위 쓰기가 겹치지 않아야 한다.
5. 순환·누락 산출물·unknown 관계: 자동 독립 처리나 임의 간선 삭제가 없어야 한다.
6. 용량이 남지 않은 소유자: 후보에서 제외되며 결과를 잘라서 수용하지 않아야 한다.
7. 검사 명령 없음·검증기 오류·실제 실패: 서로 다른 원인으로 차단해야 한다.
8. 오래된 검증 결과: artifact revision이 바뀌면 후속 해제에 사용할 수 없어야 한다.
9. 중복 이벤트·재시작: worker와 유료 요청이 중복 실행되지 않아야 한다.
10. 과도 분할: 시작/검증/통합 비용을 넣으면 더 느린 계획도 계산 결과에 드러나야 한다.
11. 지역/통합 검사: 아직 없는 통합 산출물 때문에 선행 지역 검사가 교착하지 않아야 한다.
12. 의미상 순환: 공용 계약 추출로 재구성한 새 계획만 허용하고 기존 순환 계획은 보존해야 한다.

계산 점검용 합성 예시: A=2, B=6, C=3, D=1 시간 단위, 간선 A→B, A→C, B→D, C→D.
자원 제한과 overhead를 제외하면 순차 합계 12, 의존 경로 하한 9, 경로 A→B→D다.
두 실행 슬롯의 이 예시는 A 종료 후 B/C가 함께 진행할 수 있다는 설명용 계산이다.
실제 에이전트의 속도·분 단위 측정값이 아니다. 계산 근거는 `ES/EF` 식을 따른다.

### 단계 B: 저장된 요청·응답 재생과 shadow 계획

기존 sanitized trace를 고정하고 새 planner가 동일 입력에서 어떤 후보를 내고 무엇을 거절하는지 기록한다.
재생에는 새 유료 요청이 없다. 과거 Jev 응답이 새 질문에도 타당하다고 가정하지 않는다.
새 질문의 응답은 명시된 mock으로만 검사하거나 별도 유료 실험 조건으로 구분한다.
shadow 계획은 실행 권한 없이 실제 변화와 예상 경로를 비교한다. 예상 이득과 실제 이득을 분리한다.

### 단계 C: 실제 개발 비교

| 조건 | 바뀌는 부분 | 답할 질문 |
|---|---|---|
| A: Claude 계획 + 동일 DAG 실행기 | 의미 판단 담당이 Claude | 같은 구조에서 Jev가 반복 판단 비용을 줄이는가? |
| B: 결정 규칙 + 동일 DAG 실행기 | 의미 판단을 준비된 규칙으로 제한 | 간단한 코드만으로 가능한 개선은 어느 정도인가? |
| C: Jev 계획 + 동일 DAG 실행기 | 의미 판단 담당이 Jev | 판단 품질을 유지하며 전체 완료를 개선하는가? |
| 별도 참고: 기존 실행 구조 | planner뿐 아니라 실행 구조도 다름 | 제품 전체 변경의 효과는 있는가? 직접적인 Jev 기여와는 구분 |

모든 핵심 조건에 동일 goal/spec/input snapshot, 후보 준비, 공개 검사, 작업자 모델/effort,
환경, 동시성·예산 정책, 최종 grader를 사용한다. 계획이 선택한 task 경계/실행 순서는 결과로 기록한다.
모델·노력도 선택 효과는 첫 비교 뒤 별도 요인으로 추가한다.
기존 구조와 새 구조를 동시에 바꾼 비교를 “Jev만의 효과”로 보고하지 않는다.

반복 횟수는 예비 실행 변동과 잔여 예산을 보고 사전에 고정한다. 여러 성공/실패 trial을 보존하고 조건 순서를 섞는다.
같은 머신에서 조건을 동시 실행하면 자원 경쟁이 섞이므로 우선 교차 순서로 실행하거나 자원 격리를 고정한다.
캐시 정책·모델 버전·warm/cold 시작을 기록한다. 숨은 채점 실패를 새 질문 준비에 재사용하지 않는다.

## 6. 지표·분모·산식

- **제품 성공률:** 독립 성공 trial / 사전 등록 전체 trial. 미실행·실패·불확실·채점기 오류를 각각 병기한다.
- **유효 계획률:** 모든 계획 불변 조건을 통과한 계획 / 계획 시도 전체. HTTP 성공률은 별도다.
- **전체 완료 시간:** 준비 시작부터 제품의 독립 성공 확인까지. 성공 못한 시도는 관측 종료 시간과 종료 원인을 기록한다.
- **완료 시간 비교:** 같은 조건의 성공 쌍에 대해 `T_baseline / T_candidate`; 성공률도 함께 제시한다. 미완료를 빠른 완료로 세지 않는다.
- **계획 비용:** 후보 준비 + 질문 구성 + Jev/Claude 호출 + 그래프 계산. 병렬 span의 합과 wall time은 따로 보고한다.
- **대기 시간:** 의존 산출물, 파일, 슬롯, 검증 환경별 대기. 중첩 이유는 태그로 남기고 합산용 대표 상태는 배타적으로 정한다.
- **병렬 활용:** `busy slot-seconds / available slot-seconds`. 이용 가능한 슬롯 수 변화도 분모에 반영한다.
- **재작업:** 실패 후 수정·재검증·통합에 사용한 시간과 비용. 최초 구현과 구분한다.
- **관계 판정:** 참조 라벨이 있는 후보 쌍에서 방향 포함 precision/recall; 라벨 없는 쌍과 필터에서 누락된 쌍의 표본 감사는 별도로 보고한다.
- **추정 오차:** 실제 값이 확인된 동일 작업/프로필 쌍에서 `|예측 소요 - 실제 소요|`의 평균과 표본 수. unknown을 0으로 대입하지 않는다.
- **반복 판단 대체:** 기존 프로토콜에서 필요했던 판단 중 실제 생략한 판단 ID/종류/호출 수. 모델 내부 생각의 개수를 추정해 절감으로 세지 않는다.
- **사용량·비용:** provider receipt 단위로 중복 제거. 입력/출력/캐시 생성/캐시 읽기, Jev/작업자/준비/검증/모니터를 분리한다.

실제 청구, API 환산, 월정액 배분은 서로 다른 수치다. 직접 관측할 수 없는 값은 null과 이유를 둔다.
표본 수가 적으면 분포·원시 결과를 함께 공개하고 일반화된 배율을 주장하지 않는다.

## 7. 현재 결론과 남은 검증

공식 도구들은 의존성, 자원, 작업 배정, 결과 검증을 분리한다. 이를 사용하는 구조는 문서로 구체화했다.
Jev로 의미 판단을 옮기는 것이 전체 개발 시간을 줄일지는 이 프로젝트에서 검증해야 한다.
우선 준비할 것은 검사 mapping과 artifact 계약이며, 이후 오프라인 DAG 검증을 통과한 조건에서만 실제 비교를 설계한다.
자료 접근 실패는 HEFT 원문에 한정되며 이 문서의 핵심 설계는 확인한 공식 자료와 명시된 자체 제안에 근거한다.
