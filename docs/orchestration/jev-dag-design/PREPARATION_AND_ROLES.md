# 사전 준비와 역할 분배

상태: 2026-10-10 설계 제안. 아래 경로 중 기존 파일은 읽기 전용 연결 지점이며, `제안` 경로는 아직 생성하지 않았다.
책임 역할을 정의한 문서이며 이 사이드 작업에서 에이전트를 생성한 기록은 아니다.

## 1. 준비 순서와 통과 조건

### 준비 1 — 목표와 성공 기준 고정

메인이 goal revision, 공개 명세, 요구사항 원문, 불변 제약, 사용할 도구, 예산 정책을 정한다.
완료 기준은 실행 결과와 연결한다. “작업자가 완료했다고 말했다”는 완료 기준으로 쓰지 않는다.
기존 Personal OS는 변경하지 않고 별도 개발 대상만 사용한다는 기존 경계를 새 run manifest에서도 확인한다.
제품 전체 성공 조건과 개별 산출물 준비 조건은 별도로 작성한다.

준비 산출물 제안: `run/goal.json`, `run/requirements.json`, `run/acceptance.json`.
진입점은 [기존 기술 명세](../../TECHNICAL_SPEC.md), [현재 상태](../../agents/STATE.md), [D062 결과](../D062_LIVE_PLAN.md)다.
기존 장부나 과거 실행 원본을 새 목표 문서로 덮어쓰지 않는다.

통과 조건: 모든 공개 요구사항에 ID·원문 위치·기대 결과가 있고, 범위 밖 항목과 미정 사항을 식별할 수 있다.

### 준비 2 — 테스트 설명을 실행 가능한 검사로 연결

테스트 명세별로 `check_id`, 요구사항 ID, `runner_ref`, argv/cwd, 환경, 필요한 산출물,
성공 판정, timeout 정책, 결과 파서, 버전을 정한다. 자유문 테스트 목록만 있으면 준비 미완료다.
실제 테스트 실행기 명령이 아직 없다면 구현 담당이 먼저 작성하고 검증 담당이 대조한다.

검사의 세 단계를 구분한다.

- 계약 검사: 공용 인터페이스·타입·스키마의 형식과 의미.
- 지역 검사: 작업자가 소유한 산출물과 경계 조건. 필요한 의존 산출물만 요구한다.
- 통합/최종 검사: 여러 작업 결과가 연결된 제품의 동작.

통합 검사가 나중 작업을 필요로 한다면 선행 작업의 지역 통과 조건에 넣지 않는다.
“A가 통과하려면 B 필요, B가 시작하려면 A 통과”라는 인위적 교착을 만들지 않아야 한다.
한 검사에 여러 산출물이 필요하면 독립 verification node로 표현한다.
지역 검사 통과는 제품 전체 통과가 아니다. 최종 채점 기준은 수정하거나 worker에게 숨은 정답을 제공하지 않는다.

통과 조건: 정상 예시가 통과하고 의도적으로 잘못된 산출물·누락·오래된 리비전은 실패한다.
검증기 자체 오류와 제품 동작 실패를 구별한다. 이 대조 검증을 하지 않은 gate를 준비 완료로 표시하지 않는다.

### 준비 3 — 산출물·파일·환경 계약

준비 담당은 입력/출력 artifact, 파일 read/write 범위, 공유 스키마, 공용 설정, 외부 상태를 정리한다.
여러 작업이 한 파일을 고쳐야 하면 단일 소유자에게 통합을 맡기거나, 버전이 고정된 격리 변경을 만든다.
격리 디렉터리가 다르다고 의미적 병합 충돌이 사라진다고 보지 않는다. 통합과 재검증 시간도 계획한다.
독립 작업은 별도 실행 범위로 분리하되 실행 시작 전에 소유권을 예약한다.

통과 조건: 각 결과를 누가 만들고 누가 소비하는지, 공유 파일 변경이 어디서 합쳐지는지 설명할 수 있다.
모호하면 Jev 관계 판단의 evidence-needed 항목으로 보낸다. 전체 작업을 하나의 전역 잠금으로 직렬화한 결과를 병렬 성공으로 보고하지 않는다.

### 준비 4 — 모델·노력도·실행 자원 프로필

현재 연결 지점은 [정본 계약 안내](../contracts/README.md), [모델 목록](../contracts/models.v2.json)이다.
실행 시 실제 로딩한 버전·해시를 기록한다. 카탈로그에 존재하는 것과 계정에서 호출 가능한 것은 별개다.
프로필에는 API/CLI adapter, 요청 모델과 실제 응답 모델, effort 지원, 도구 허용 범위, 계정 가용성,
입력 제한, 실행 시간 이력, 토큰·비용 근거, 검사 성공 이력을 연결한다.

소요 이력이 없으면 추정 시간 `null`과 사유를 남긴다. 샘플 수가 다른 평균을 같은 신뢰도의 값으로 쓰지 않는다.
프로필 지원 여부를 확인하는 호출과 실측 성능 평가 호출을 구분한다.
최대 작업자, 동시 슬롯, provider rate limit, CPU/RAM, 파일 lease, 검증 슬롯을 서로 다른 자원으로 관리한다.

통과 조건: 요청한 모델·effort가 실제 adapter로 전달됨을 확인할 수 있고 미지원 조합은 실행 전에 거절된다.
첫 비교에서는 작업자 프로필을 고정하는 것이 분할 효과를 분리하는 설계 제안이다.

### 준비 5 — Jev 연결과 문서 계약

공식 연결·한도·재시도 근거는 [조사 R1](RESEARCH.md#r1-jev-api)에 짧게 정리했다.
운영 전 실제 클라이언트의 최종 목적지와 현재 계정 모델 목록을 확인하고 서버 비밀 환경만 사용한다.
이번 문서 작업에서는 키 파일을 읽거나 모델 조회·추론을 실행하지 않았다.

새 질문 초안 정본은 [ARCHITECTURE §4.2](ARCHITECTURE.md#42-고정-영어-질문과-선택값--처리-함수)다.
구현 시 제안 경로 `docs/orchestration/contracts/dag-routing.v1.json`에 질문 ID, 영어 원문,
선택지, handler ID, 변수, unknown 조건, 버전을 둔다. 이 파일은 아직 생성하지 않았다.
기존 질문 파일의 의미를 바꾸지 않고 새 모드로 연결한다.
질문 state에는 원문 발췌·후보·제약·현재 예약·검사 준비 상태를 담고, 원본 경로와 hash는 추적용으로 연결한다.

통과 조건: 문서 → loader → 실제 요청 → 선택된 handler를 한 결정 ID로 추적할 수 있다.
모의 응답의 선택지·용량 위반·누락 필드·불확실한 응답도 검사한다. 모의 성공은 실제 모델의 제약 준수 증거가 아니다.

### 준비 6 — 기록·대시보드·재생

비공개 run 디렉터리에 입력/프로토콜/질문/응답/산출물/검사/사용량을 연결한다.
타임스탬프와 경과 시간은 출처를 남기고, 프로세스 간 시간축 정렬 한계도 명시한다.
상태 변경은 event ID와 attempt ID로 중복 방지한다. 재시작 시 장부·예약·실행 상태를 복원한다.
결과를 모르는 유료 요청을 다시 보내는 것이 복구 절차가 되지 않도록 한다.

통과 조건: 저장된 응답을 재생했을 때 같은 task/edge/handler/검사 해제가 나오고, 화면 합계가 원본과 맞는다.
다른 조건에서 만들어진 오래된 통과 기록을 현재 결과로 재사용하지 않는다.

## 2. 시스템을 사용하는 동안의 책임

### 메인 컨트롤러 소유자

목표·범위·실행 정책·최종 통합의 책임자다. 불명확한 사용자 요구와 실험 조건 변경을 관리한다.
정상적인 Jev 선택마다 다시 의미 판단하지 않고 제약 검증과 실행 상태로 다음을 진행한다.
최종 성공은 검증 결과와 요구사항 보존을 확인해 보고한다.

### 준비 담당

원문 요구사항·작업 후보·산출물 인터페이스·근거를 작성한다. 새 아키텍처 설명이 필요할 때만 자유문 생성한다.
요구사항별 기대 결과와 문서 경로를 유지하며, 질문을 실행 때마다 다시 만들지 않는다.
같은 후보가 반복 거절되면 실패 근거를 포함해 후보 집합을 수정하고 revision을 올린다.

### Jev 판단 서비스

사전 질문에 따라 분해 후보, 관계, 소유자, 모델/effort, 실패 후 행동 후보를 선택한다.
외부 도구 실행·키 접근·검사 성공 선언·전체 작업 종료의 최종 권한은 갖지 않는다.
여러 의미 판단을 같은 state에서 묶을 수 있지만 결합 제약은 별도 검증해야 한다.

### DAG·스케줄러

코드 역할이다. 그래프/소유권/슬롯/검사 준비·예산을 검사하고 시작 시점을 결정한다.
명시된 관계와 시간 모델로 계산 가능한 것은 모델에 묻지 않는다.
관계가 unknown이거나 검증 증거가 없으면 준비 상태를 생성하지 않는다.

### 구현 작업자

배정된 요구사항, 실제 입력 산출물, 수정 범위, 검사 ID, 반환 형식을 받는다.
공용 명세 중 관련 원문은 한 번 전달하고 참조 위치를 함께 준다.
새 의존성·범위 충돌을 발견하면 근거와 제안만 제출하고 다른 작업자의 파일을 임의로 수정하지 않는다.
반환: 산출물/패치, 사용한 입력 버전, 실행한 검사와 원출력, 남은 문제, 소요·사용량.
작업자의 자체 검사 보고는 독립 검증 결과와 구분한다.

### 검증·통합 담당

등록된 검사를 정확한 산출물 버전에서 실행하고 통합 결과를 다시 확인한다.
제품 구현 담당이 자신의 실패를 통과시키도록 기대값을 바꾸지 못하게 책임을 분리한다.
검사 미실행/실패/검증기 오류/근거 부족을 별도 상태로 기록한다.
Jev를 검토 보조로 써도 코드 검사와 독립 최종 채점을 대체하지 않는다.

### 관측·기록 담당

원본 events/receipts/checks만 읽어 계획·대기·실행·수리·검증·통합 시간을 집계한다.
작업자와 Jev, 검증, 모니터의 비용을 구분하고 실제 청구가 없으면 환산임을 표시한다.
프로세스 상태·로그 무변화·실제 실패를 구분한다. 집계 오류를 발견하면 원본을 보존하고 정정한다.
매 이벤트마다 새 모니터 모델을 호출하지 않는다. deterministic 집계와 의미적 검토를 구분한다.

## 3. 이 시스템을 구현할 때의 개발 역할 분배 제안

역할마다 입력·출력·소유 파일·검증·인계 조건을 문서로 확정한 후 담당자를 배정한다.
아래는 후속 개발용 작업 묶음이며 지금 서브에이전트를 생성한 것은 아니다.

1. **계약/준비 담당:** requirement/artifact/task/edge/check/event schema와 영어 질문 문서. 스키마를 먼저 고정하고 작은 공통 fixture를 제공한다.
2. **판단 어댑터 담당:** 기존 Jev client·장부를 재사용하는 문서 로더와 선택지 구성/용량 예약. 기록된 응답으로 오프라인 재생한다.
3. **그래프/스케줄러 담당:** 순환·준비 집합·임계 경로·슬롯/파일 예약·부분 재계획. 가짜 시계로 실행 순서를 검증한다.
4. **검증 연결 담당:** 공개 검사 mapping·리비전 gate·공유 검사 준비 조건·수리 분류. 정상/결함 산출물 대조로 gate를 검증한다.
5. **관측/UI 담당:** 위 event 계약을 읽는 집계와 간단한 대기 이유/임계 경로 표시. 실제 모델 없이 fixture로 작업할 수 있다.
6. **독립 검토 담당:** 요구사항 누락, 숨은 전역 barrier, 용량 초과, 잘못된 검증 해제, 비용 누락을 검사한다. 구현자의 통과 로그만 신뢰하지 않는다.
7. **메인 통합 담당:** 파일 소유권·계약 버전 충돌 조정, 관련 회귀, 실험 manifest와 최종 보고.

병렬 시작 경계: 계약 fixture가 준비되면 어댑터/스케줄러/검증/UI를 독립 구현할 수 있다.
계약 변경은 버전을 올리고 소비 담당자에게 영향 목록을 제공한다. 공유 스키마에 여러 작성자를 두지 않는다.
개발 역할 수와 제품 실행 작업자 수를 혼동하지 않는다.

## 4. Claude·Codex 진입점과 인계

현재 저장소 안내는 [AGENTS.md](../../../AGENTS.md), [CLAUDE.md](../../../CLAUDE.md), [계약 README](../contracts/README.md)다.
이 사이드 작업은 해당 파일을 변경하지 않았다. 메인이 채택할 때 새 설계 링크만 적절한 진입점에 연결한다.
worker의 자동 문서 탐색에 의존하지 않고 목표/역할/필요 계약의 내용과 경로·해시를 명시 전달한다.

인계 문서 최소 필드:

```text
goal_revision, role_id, graph_revision, owned_task_ids
source_doc_paths_and_hashes, artifact_revisions
write_scope, active_leases, running_processes
verified_checks, failures, uncertain_request_outcomes
changed_files, remaining_work, next_exact_read_or_check
budget_ledger_ref, unresolved_decisions
```

문맥이 부족하면 안전한 작업 경계에서 상태를 저장하고 기존 담당의 쓰기를 종료한 뒤 새 담당에게 넘긴다.
정확한 메모리 잔량을 계측했다고 가정하지 않는다. 새 담당은 문서와 실제 파일을 대조하고 진행 중 유료 요청을 중복 실행하지 않는다.
메인은 압축/인계 후 목표·성공 기준·현재 DAG·미해결 의무부터 확인한다.

## 5. 첫 구현의 권장 범위와 다음 실행 조건

첫 범위는 기존 runner 위에 새 planner/graph layer와 검증 연결을 넣는 별도 모드다.
Ray/Dask 전체 도입은 이번 조사에서 확정하지 않는다. 현재 단일 호스트의 기존 실행 경로에서 개념을 먼저 검증한다.

순서: 실행 검사 mapping → 최소 artifact/task schema → DAG 검증/가짜 시계 스케줄 → Jev 응답 재생 → 변경 없는 shadow 계획 → 별도 실험 조건 동결 → 실제 개발 비교.
새 실험의 표본 수·가용 모델·분할 후보 정책·시간 추정 정책·예산 사용은 메인이 현재 상태를 보고 고정한다.
이 문서만으로 유료 호출, 최대 동시성 확대, 신규 모델 사용을 시작하지 않는다.
