# D085 — 복수 owner(C)와 import·문법 오류 직접 수리 (구현·오프라인 재현, 유료 호출 없음)

사용자 지시: "import 오류는 직접 수정으로 가자. C로 수정을 해서 가보는 걸로 하고, 이후에 동작이 효과적인지 다시 분석." 직접 수정 방식은 사용자가 고른 "수리 작업자 바로 투입"이다. 막힌 검사는 Jev owner 추론을 건너뛰고, 코드 생성 파일(generator + 템플릿)을 고칠 수 있는 수리 작업자를 바로 보낸다. 작업자는 전체 오류와 생성된 파일 내용을 받는다.

manifest: `benchmarks/e2e-swe/manifests/d085-direct-repair.json`. `d083-repair-fixes.json`과 다른 점은 `repair_feedback`의 두 값과 설명뿐이다.

## 1. C — `owner_alternatives: owner-probability-v1`

질문 형식은 바꾸지 않는다. Jev choice 답에는 이미 모든 artifact의 확률이 들어 있다. 이 확률을 그대로 쓴다.

- 실패 하나(추론된 답)마다, 선택되지 않은 artifact 중 확률이 **0.2 이상**이고 **선택 artifact 확률의 0.4배 이상**이면 2차 owner로 본다. `unknown`과 unknown 답은 제외한다.
- 2차 owner 중 union에 없는 artifact를 최대 2개 더한다. 순서는 지목한 실패 수, 그다음 확률 합이다.
- 새 후보 `repair-inferred-owners+owner-alternatives`를 union 뒤에 추가한다. 두 범위 봉인(`inferred_ownership`, `causal`)은 D083 확장과 같은 방식으로 다시 발급한다. 확률은 봉인된 `proof.answers`에서 읽는다.
- 범위 규칙의 우선순위: worker-mentioned 확장 > owner-alternatives > union. worker-mentioned 확장은 owner-alternatives 후보 위에 만든다.
- 구현 위치: `adaptive-inferred-scope.mjs`(`ownerProbabilityAlternatives`)와 `adaptive-dag-execution.mjs`(`withExpandedScope`). `adaptive-inferred-repair.mjs`는 prompt policy v1–v3 pin이라 바꾸지 않았다.

## 2. 직접 수리 — `check_error_repair: generation-direct-v1`

계약은 `docs/orchestration/contracts/adaptive-check-error-repair.v1.json`, 구현은 `src/orchestration/adaptive-check-error-repair.mjs`이다.

1. 공개 검사가 `SyntaxError`·`IndentationError`·`TabError`·`ImportError`·`ModuleNotFoundError`로 테스트 전에 멈추면 발동한다. 실행당 1회.
2. owner 추론(Jev)과 수리 후보 선택을 건너뛴다. 범위는 코드가 정한다. 경로에 `templates/` 디렉터리가 있거나 파일 이름이 `generator.py`인 artifact다. D066 catalog에서는 A16–A21이고, 소유 task는 보통 4개다.
3. 진단: runner가 같은 고정 이미지·후보·고정 검사기로 막힌 suite를 한 번 더 돌린다(`scripts/diagnose-check-error.py`). 예외가 나면 다음을 남긴다.
   - traceback
   - 생성된 파일 목록
   - 오류가 가리키는 생성 파일 내용(파일당 12,000자, 최대 4개)
   - 컴파일되지 않는 생성 파일
   - 없는 모듈의 가장 가까운 부모 `__init__.py`

   같은 오류 메시지는 한 번만 진단하고, 서로 다른 오류는 최대 3개까지 진단한다. 이것은 검사가 아니고 증거로 쓰지 않는다. 공개 fixture만 쓴다. 진단이 실패해도 실행은 계속되고, 작업자는 보고된 오류만 받는다.
4. 후보는 causal 봉인에 추가해 다시 봉인한다. 기존 causal 검증기를 그대로 통과한다. 작업자 packet은 causal 작업자 packet에 `check_error_repair`(오류와 진단)와 고정 지시를 더한 것이다.
5. 이 회차는 수리 2회와 별도로 1회 더한다(최대 3회). 이후 회차는 일반 owner 추론 경로를 탄다.

## 5. 결론과 다음

- 직접 수리는 기록된 실패 2건(d082-02, d080-03)의 원인이었던 단계를 피하고, 원인 artifact를 범위에 넣고, 원인 파일 내용을 작업자에게 준다. 오프라인 근거로는 효과가 있을 가능성이 높다. 실제 수리 성공은 미측정이다.
- C는 필요한 artifact를 한 회차 일찍 넣는 경우가 11번 중 2번(+1번 미상)이다. 필요 없는 추가는 6번이다. 이득은 회차 절약, 비용은 작업자 추가와 회귀 위험이다. 효과는 섞여 있다.
- 유료 측정은 조건당 3회 이하로만 한다(사용자 지시). 아직 실행하지 않았다. 아래 6·7절이 이후 추가됐다. 막힌 검사는 실행 15개 중 3개에서만 나왔다. 그래서 3회로는 직접 수리가 한 번도 발동하지 않을 수 있다. C는 R10.02가 7/13 빈도라 발동할 가능성이 높다.

## 6. 평평한 owner 답 — 1회 재질문, 안 되면 작업자가 선택 (`owner_tiebreak: flat-reask-v1`)

사용자 지시: 확률이 고르게 퍼진 경우 추가 정보를 받아 다시 고르고(1회), 그래도 안 되면 에이전트가 직접 선택한다.

- **평평함의 기준**(`adaptive-owner-tiebreak.v1.json`): 추론된 답의 선택 확률이 0.4 미만이고, `unknown`이 아닌 다른 artifact가 0.1 안에 있을 때다(소수 6자리 반올림). 동점 집합은 선택 artifact와 0.1 안의 artifact이며, 확률 순으로 최대 3개다.
- **재질문(1회)**: 회차마다 평평한 실패를 모두 모아 Jev에 한 번 묻는다(stage `repair_owners`). 질문 하나는 실패 하나이고, 선택지는 동점 artifact와 `unknown`이다. 추가 정보는 동점 artifact의 **실패 당시 소스 원문**(파일당 8,000자, 합계 48,000자, 잘림 표시), catalog 인터페이스, 첫 답의 확률이다. 요청 형태가 다르므로 owner 설명 덧붙이기(owner criteria)를 거치지 않는 별도 콜백 `decideOwnerTiebreak`로 보낸다.
- **결과 처리**
  - 둘째 답이 평평하지 않으면 그 artifact를 union에 더한다.
  - 다시 평평하거나 `unknown`이면 동점 artifact를 모두 쓰기 범위에 넣는다. 수리 작업자(에이전트)는 "Jev가 소스로도 구분하지 못했다. 어느 것을 고칠지 직접 판단하고, 원인이 아니라고 보는 것은 그대로 두라"는 지시를 받는다. 별도의 Claude 선택 호출은 만들지 않았다. 작업자가 고칠 파일을 고르는 것이 곧 에이전트의 선택이다.
  - 둘째 호출이 알려진 실패로 끝나면 작업자가 선택하는 경로로 간다. 결과가 불확실하면 다른 owner 결정과 같이 그 회차를 불확실로 멈추고 재전송하지 않는다.
- 후보 `repair-inferred-owners+tiebreak`를 다시 봉인한다. C(`owner_alternatives`)는 tie-break 후보 위에 만들고, 평평했던 답에는 비율 규칙을 쓰지 않는다. 범위 규칙의 우선순위: worker-mentioned > owner-alternatives > tiebreak > union.
- 원래 선택 artifact는 빼지 않는다(덧붙이기만 한다). 봉인된 첫 답과 작업자 상세 범위를 그대로 두기 위해서다.
- **과거 발동 빈도**: owner 결정 11개, 답 105개 중 평평한 답 3개(2개 실행)
  - d080-01 r0: A14 0.23 / A09 0.22 / A11 0.20. C가 이 답에서 A09·A11을 더하던 것이 재질문으로 바뀐다. 불필요 추가가 6건에서 5건으로 준다.
  - d082-06 r1 답 2개: A07 0.36 / A21 0.36, A07 0.39 / A21 0.35. D084가 필요하다고 본 A21이 재질문 결과나 작업자 선택 대상으로 들어간다.
  - 재질문의 실제 답은 유료 호출 전에는 알 수 없다.
- 검증: mock 실행 1개(해결 / 다시 평평 / 알려진 실패 / 불확실), 기준 단위 테스트 1개(과거 답 5개). 회귀 1366/1370(실패 1은 root 전용 refund 테스트, 건너뜀 3). `--probe` ready. `adaptive-dag-runner.mjs`가 다시 바뀌어 v11 pin을 갱신했다. v11은 아직 어떤 실행에도 쓰이지 않았으므로 새 버전을 만들지 않고 v11 안에서 다시 고정했다.

## 7. 문법·import 오류의 정적 분석 (고안과 오프라인 측정, 런타임 미연결)

문법과 import 오류는 테스트를 돌리지 않아도 검증할 수 있다. 그래서 정적 smoke(`scripts/static-generation-smoke.py`)를 만들었다. 고정 이미지에서 후보를 설치하고, 공개 fixture 7개마다 client를 생성한 다음, 생성된 모든 모듈을 `compile`하고 새 interpreter에서 모두 import한다. assertion은 실행하지 않는다.

과거 회차 후보 26개에 실제로 돌렸다(과금 없음).

| | smoke 실패 | smoke 통과 |
|---|---|---|
| 공개 검사가 import·문법으로 막힘 (4) | 3 (d080-03 r0, d082-02 r0·r1) | **1** (d082-01 r0: 없는 모듈) |
| 막힘 없음 (22) | 0 | 22 |

- 비용: 후보당 7.1–8.5초(CPU 2, 그중 설치 약 5초).
- 놓친 1건: smoke는 존재하는 파일만 import하므로 "생성됐어야 하는데 없는 모듈"(`api/transport`)은 찾지 못한다. 이를 잡으려면 fixture의 tag와 operation으로 기대 모듈 목록을 만들어야 하는데, 그건 공개 검사를 다시 구현하는 일에 가깝다.
- 추가로 보인 것: d080-03에서는 smoke가 fixture 3개(cli·http·models)에서 같은 `*,` 오류를 찾았다. 공개 검사에서는 막힌 검사가 1개뿐이었다. 공개 검사가 import하지 않는 생성 모듈의 잠복 오류도 smoke는 찾는다. 완료된 실행 9개의 최종 후보에서는 잠복 오류가 0건이었다.
- 쓸 수 있는 곳
  1. **효과 측정(오프라인)**: 직접 수리 회차의 성공 기준을 "smoke 통과"라는 정적 이진값으로 둘 수 있다. 유료 실행 뒤 회차별 후보에 돌리면 직접 수리가 문법·import 문제를 실제로 없앴는지 공개 검사와 따로 판정할 수 있다. 런타임 변경이 필요 없다.
  2. **런타임 gate(미구현)**: 수리 작업자 직후 공개 8검사 전에 smoke를 돌리고, 실패하면 같은 회차에서 다시 고치게 하는 방식이다.
- **판단**(사용자 확정: 넣지 않음): 2는 지금 추가하지 않는 것을 권한다. 막힘 4건 중 3건은 공개 검사도 같은 회차에 잡고, 직접 수리 경로가 그 결과로 이미 발동한다. 잠복 오류로 실패한 완료 실행도 없었다. 1은 스크립트만으로 가능하므로 유료 측정 분석에 쓴다.

## 8. 재질문 소규모 유료 측정 (5회 반복)

사용자 지시: 1번(재질문)은 유료 호출로 5회 반복해 결과를 확인한다. 정적 분석은 넣지 않는다(스크립트는 분석용으로만 남는다).

## 10. d085-cloud-01의 공개↔독립 차이 (분석만, 수정하지 않음 — 백로그)

사용자 지시: 01의 공개 93/93 · 독립 62/63 차이를 보고 문제만 보여 준다. 고치지 않는다. 작은 문제면 백로그로 둔다.

- **실패 1건**: 독립 채점의 `field_prefix` 검사다. 숫자로 시작하는 속성 이름에 설정한 접두사를 붙인 attribute 이름이 기대와 다르다. 숨김 검사의 내용은 계획·수리·검토 어디에도 넣지 않았다. 아래 예시는 공개 검사의 `3value`다.
- **원인**: A06 `pyclientgen/naming.py`의 단어 분리 정규식 마지막 대안이 `[0-9]+`다. 그래서 숫자와 뒤따르는 소문자를 나눈다.
  - `snake_case("3value")` → `3_value` → `field_3_value`. 02·03 후보는 `field_3value`다.
  - `a1b` → `a1_b`처럼 숫자 뒤 소문자도 끊는다.
  - 명세의 snake_case 경계는 공백·식별자 아닌 문자·소문자→대문자·약어 경계뿐이다. 숫자→소문자는 경계가 아니다.
  - 같은 후보의 `config.py`는 `[0-9]+[a-z]*`를 써서 자기 안에서도 규칙이 갈린다. snake_case 구현이 두 artifact에 중복돼 있다.
- **공개 검사가 놓친 이유**: `http_client.py`의 `verify_config_models`는 `3value` 속성이 접두사로 **시작하고** 유효한 식별자인지만 본다. 정확한 이름은 보지 않아 `field_3_value`도 통과한다.
- 01 후보의 이 코드는 회차0부터 최종(명세 검토 채택본)까지 같다. 명세 검토도 잡지 못했다.
- **크기**: 정규식 한 대안(`[0-9]+` → `[0-9]+[a-z]*`)의 문제이고, 수정은 한 줄 규모다. 구조 문제는 아니지만 두 가지 갭이 드러났다. 공개 검사가 정확한 attribute 이름을 보지 않는 점, 그리고 snake_case 구현이 중복된 점이다.
- **백로그 후보**(미결정): (a) 공개 검사에 정확한 attribute 이름 assertion 추가(공개 검사 버전 변경 필요). (b) snake_case를 한 artifact에만 두도록 catalog·명세에서 유도.
