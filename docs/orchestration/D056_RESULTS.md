# D056 — 재귀 작업·테스트 계획 검증

2026-10-10. 구현과 실제 계획 실험을 마쳤다. API 호환성은 확인했지만, 적정한 분할 계획은 완성하지 못했다. 마지막 실행은 `PLANNING_DECISION_LIMIT`에 따른 `partial`이다. 제품 효율 개선은 측정하지 않았다. [구조화 기록](../decisions/D056.md).

## 구현과 측정 경계

Jev가 현재 노드의 자식 수 1~5를 선택하고, 2~5이면 기준 의무와 나머지 의무의 책임자를 정한다. 코드가 분할의 누락·중복·진행 여부를 검사한 뒤 자식을 다시 검토한다. 부모는 집계용으로 남고, 최종 작업 목록과 테스트 명세 목록을 각각 저장한다. 고정 영어 질문은 [v2 계약](contracts/recursive-task-tests.v2.json), 구조는 [구현 설명](D056_IMPLEMENTATION.md)이다.

입력은 공개 OpenAPI 과제의 80개 출처 연결 의무와 85개 테스트 명세다. 제품 구현 작업자, 실제 테스트 실행, 독립 채점과 Claude 계획 대조는 이 단계에서 실행하지 않는다. 원문·테스트 설명 준비에 든 개발 작업은 Jev 호출 비용에 포함하지 않는다.

## 실제 분할 결과

- 요구사항 80/80개가 leaf에 정확히 한 번씩 배정됐다. 테스트 명세 85/85개와 원래 예상값을 보존했다. 이는 구조 보존 결과이며, 의미상 완전성이나 실제 테스트 통과가 아니다.
- 분할 9회가 확정돼 전체 노드 36개, leaf 27개, 최대 깊이 3이 됐다. 준비 상태인 20개 leaf는 모두 단일 의무라 코드가 선택을 우회한 경우다. Jev가 더 나눌 필요 없다고 판단한 것이 아니다.
- 7개 leaf는 검토 대기다. 37개·18개 의무가 남은 두 묶음과, 1개씩 가진 다섯 묶음이다. 37개 노드를 재분할하던 중 판단 한도 240회에 도달해 미완성 교체안은 반영하지 않았다.
- 유료 `child_count` 10/10개가 분할을 선택했다. 유지 선택 `1`은 0/10개다. 이 관측만으로 모델 내부 이유나 다른 과제의 분할 성향을 확정할 수는 없다.

## 시간·토큰·비용

영수증 240개를 합산했다. [비용 분해](../../benchmark-runs/d056-recursive-03/cost-breakdown.json)의 분모는 이번 성공한 계획 호출 전체다.

| 판단 단계 | 호출 | 실제 입력 토큰 | 토큰팩 기준 환산 USD |
|---|---:|---:|---:|
| 자식 수 선택 | 10 | 119,592 | 0.0717552 |
| 자식의 기준 의무 선택 | 35 | 548,451 | 0.3290706 |
| 나머지 의무의 책임자 배정 | 195 | 4,564,606 | 2.7387636 |
| 계획 전체 | 240 | 5,232,649 | 3.1395894 |

출력은 33,144토큰이다. 환산은 `입력 토큰 × USD0.60 / 1,000,000`이며, [Jev 공식 토큰팩 가격](https://jev-ai.pro/pricing)의 USD9/15M 기준이다. 실제 월정액 청구액·호출별 배분액은 `null`이다. 앞선 실패의 알려지지 않은 추론 토큰, 하네스 개발과 사전 테스트 설명 작성 비용은 이 표에 포함하지 않는다.

계획 전체는 249.348초, `inference_finished.duration_ms`로 측정한 개별 판단 요청 구간 합계는 181.819초였다. 이 구간의 중앙값은 760ms, p95는 966ms다. 분석 JSON의 `http_*` 필드는 이 이벤트 구간을 가리킨다. 별도로 클라이언트의 `receipt.durationMs`만 합산하면 181.573초이며, 둘의 0.246초 차이를 같은 측정으로 취급하지 않는다.

계획 전체와 요청 이벤트 구간의 차이 67.529초에는 모델·잔액 조회, 직렬화·복원 검사, 장부·파일 기록, 로컬 계획 처리가 들어간다. 각 항목 시간을 따로 계측하지 않았으므로 전부 잔액 조회 시간이라고 귀속하지 않는다. 단계별 `wall_ms` 합계와 전체 시간도 계측 경계가 다르다.

책임자 배정은 호출 195/240=81.25%, 입력 4,564,606/5,232,649=87.2332%를 사용했다. Jev 한 번의 응답은 짧지만 같은 큰 state를 들고 의무를 하나씩 배정하는 구조가 반복 비용을 만든다. 마지막 미확정 교체안에 든 10호출·178,450입력도 전체 비용에 포함했다.

[독립 감사](../agents/D056_REVIEW.md)의 이벤트·영수증 대조에서 80개·64개·58개 의무를 나누는 세 번의 배정 과정이 205/240호출, 입력 4,906,860/5,232,649토큰을 사용했다. 현재 검증은 누락 없는 엄격한 분할을 요구하지만, 큰 자식이 충분히 작아졌는지는 요구하지 않는다. 그래서 80개 중 64개가 한 자식에 남아도 구조 검사를 통과한다. 이것은 지켜진 구조 조건과 달성하지 못한 효율 조건의 차이다.

최종 [예산 스냅샷](../../benchmark-runs/d056-recursive-03/budget-after.json)은 누적 6,669,999/10,000,000 입력 토큰, 잔여 3,330,001, 예약 0, 미정산 0이다. 이번 실행은 토큰 예산이나 시간 초과가 아니라 판단 횟수 보호 한도에서 끝났다.

## 별도 Opus 검토

`node scripts/monitor-d056.mjs --spend benchmark-runs/d056-recursive-03`으로 별도 `claude-opus-5-5`, medium을 호출했다. [원본 보고서와 영수증](../../benchmark-runs/d056-recursive-03-monitor/result.json)의 결과는 `attention`이다. 54.575초, 일반 입력 2토큰·1시간 캐시 생성 68,169토큰·캐시 읽기 0·출력 5,771토큰, CLI 보고 API 환산 USD0.66078이다. Jev 계획 비용과 분리하며 실제 추가 청구액은 미확인이다.

모니터가 지적한 과대·과소 분할, 실제 테스트 미실행, 미확정 의존 관계는 후속 설계에서 다룰 문제다. 현재 수정 범위는 기존 D052의 보수적인 관련 파일 목록으로, 정확한 수정 소유권이 아니다. `write_serialization`도 계획 메타데이터다. 실행 전에 원문 의무와 수정 범위를 대조하고 실제 의존 관계·공유 파일 작업 순서를 확정해야 한다. 모니터 의견을 자동으로 요구사항이나 실행 명령으로 채택하지 않는다.

독립 재검토에서 공유 파일 순서는 강한 직렬화 제약을 만들지만 전체가 단일 직렬 순서는 아님을 확인했다. 모니터가 제안한 의존 화살표와 파일 범위 보정은 추가 요구사항 대조가 필요한 검토 의견이다. 또한 응답의 모델 문자열은 `typesafe-ai/jev` 152회, `typesafe/jev-1.13-20260917` 21회, `jev-1.13.0` 67회였다. 모든 요청은 `jev-latest`이며, 별칭 표기의 차이만으로 실제 백엔드 모델 변경을 단정하지 않는다.

모니터의 집계 관련 지적은 코드·이벤트로 다음처럼 해석해야 한다.

- `feasibility_states=104094`는 모든 탐색의 누적 합계다. `max_feasibility_states=10000`은 한 번의 탐색 한도이므로 두 수만 비교해 한도 무시라고 결론 내릴 수 없다.
- `reviewed_nodes=30`에는 마지막 미확정 교체안의 개수 판단도 포함된다. 공개된 review 29개와 계측 범위가 다르다.
- `deterministic_choices=25`에는 leaf 처리 20회 외에 기준 의무 선택의 단일 후보 우회 5회가 포함된다.
- 원본의 `stop_code=null`은 외부 예외 필드만 채운 결과다. 중단 사유는 이미 `issues`에 있었다. 이후 실행기가 엔진 중단 코드도 최상위에 표시하도록 보완했다. 원본 결과는 변경하지 않았다.

이 혼동을 줄이기 위해 이후 모니터 입력에는 지표 정의와 간결한 이벤트 집계를 추가했다. 이번 모니터 원본은 그대로 남기며, 같은 검토를 유료로 다시 호출하지 않았다.

## 다음 수정 대상 — 아직 구현·재측정하지 않음

1. `1=유지`가 모든 의존 관계의 확정을 요구하는 현재 문장을 재검토한다. 추가 분할의 이득과 정보 부족을 구별해야 한다. 분할만 반복해도 미확정 의존 관계는 해결되지 않는다. 이 문장이 실제 분할을 유발했다는 인과 효과는 아직 검증하지 않았다.
2. 기준 의무를 고정한 뒤 호환되는 책임자 질문을 한 요청에 묶는 방식을 비교한다. 현재처럼 모든 의무를 순차 호출할 필요가 있는지 검사하되, 누락·중복·순환 검증은 유지한다. 다중 질문도 모델별 입력 한도와 API 질문 수 제한 안에서 시험해야 한다. 배정을 시작하기 전에 전체 배정을 끝낼 잔여 호출 예산을 검사하고, 판단 입력에도 잔여 예산과 관측된 계획 비용을 보여주는 안을 검토한다. 이번처럼 비용을 쓴 뒤 교체안을 확정하지 못하는 경우를 줄이려는 목적이다.
3. 자식 수보다 검증 가능한 결과 단위, 공유 파일, 실제 의존 관계를 먼저 정리한다. 수정 범위와 의존 관계가 준비되기 전에는 이 목록을 제품 작업자에게 실행시키지 않는다.
4. 그 후 같은 입력·고정 작업자·독립 채점으로 Claude 계획과 비교한다. 현재 계획 1회나 바이트 감소만으로 전체 비용·속도 개선을 주장하지 않는다.

## 검증 도구 자체의 보완

- 첫 진단기는 오류 분류와 해시만 보존해 실제 원인을 구별하지 못했다. 이후 허용된 오류 필드에서만 짧은 내용을 가져오고 키·인증 문자열을 제거하는 기능을 추가했다. 실제 원인은 세 번째 진단에서 확인했다.
- 첫 실패 영수증의 본문 크기가 빠져 초기 분석 값이 `null`이었다. 원래 분석을 보존하고 이벤트로 계산한 `analysis-v2.json`을 추가했다. 새 영수증에는 크기를 기록한다.
- 첫 실행은 소스 해시만 고정했다. 이후 변경된 두 파일을 역패치로 복원해 9/9 해시 일치를 확인했다. [복원 기록](../../benchmark-runs/d056-source-recovery-01/recovery.json)은 사후 복원임을 명시한다. 두 번째 실행부터 원본 바이트를 실행 전에 저장한다.

실제 호출 명령은 [구현 문서](D056_IMPLEMENTATION.md)를 따른다. `--spend`는 유료 추론을 허용하며 기존 장부를 사용한다. 과거 실패 요청은 자동 재전송하지 않는다.

제품 구현·제품 테스트·전체 효율 비교는 미실행이다. 계획 자체도 `partial`로 남겼으며 유료 재개는 하지 않았다. 개인 Personal OS/Vault는 수정하지 않았다. 비공개 실행 로그·소스 사본, 분리된 CLI 임시 디렉터리와 미커밋 변경을 보존한다. 새 제품 컨테이너, 커밋과 푸시는 없다.
