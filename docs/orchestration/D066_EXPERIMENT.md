# D066 — 재귀 분해·관계·수리의 동일 조건 비교

2026-10-11 Asia/Seoul. 상태: 실행 전 프로토콜. 최신 사용자는 기존 E2E-SWE `openapi_python_client` 과제로 자유 재귀 분해, 관계 판단, 자동 수리, Claude 단독 대비 효율을 모두 실제 비교하라고 요청했다. [역할 계약](../agents/D066_PARALLEL.md)에 따라 구현·실행·독립 검토·스킬 관리를 분리한다. D065의 종료 뒤 재실행 금지는 그 완료된 시도에 대한 경계이며 이번 새 요청을 막는 승인이 아니다. 과거 실행·후보·원본 Personal OS/Vault는 보존한다.

## 비교 단위와 고정 조건

| 조건 | 재귀 분해 | 관계 선택 | 공개 실패 수리 선택 |
|---|---|---|---|
| `claude_all` | Claude | Claude | Claude |
| `jev_split` | Jev | Claude | Claude |
| `jev_split_relations` | Jev | Jev | Claude |
| `jev_all` | Jev | Jev | Jev |

각 조건 1회, 위 순서로 실행한다. 조건 사이는 직렬, 조건 안의 실제 구현은 최대 동시 2개다. 동일한 공개 원문, 새 후보 목록의 바이트, 영어 질문 계약, 작업자 지시·모델·노력도, 공개 검사 버전, Docker 이미지, 수리 기회를 사용한다. Claude 판단·후보 준비·구현 모델은 `claude-opus-5-5`, effort `medium`; Jev는 `jev-latest`, 직접 목적지 `https://jev-ai.pro/api/v1/systemone`이다. 도구 없는 Claude 판단기는 Jev와 같은 질문·후보에 같은 typed 답을 낸다. 이것은 동일 구조의 Claude 판단 기준선이며 제한 없는 일반 Claude Code 사용 전체와의 비교는 아니다.

독립 채점 전에 다른 조건의 후보·실패·모델 답을 다음 조건에 넣지 않는다. 공통 원문·후보 준비 이후의 각 조건은 새 폴더와 세션에서 시작한다. 순서, 공급자 상태, 캐시의 교란을 기록한다. 각 1회 결과로 일반적인 우월성이나 통계적 유의성을 주장하지 않는다.

## 실제로 자유롭게 선택하는 범위

이전 16개 파일 배정 경계는 재사용하지 않는다. 원문과 80개 공개 요구사항의 ID·문장에서 Claude가 새 구현 단위·산출물·인터페이스 후보를 한 번 만든다. 이전 `write_scope`, 인터페이스, DAG, 완성 코드는 후보 준비에 넣지 않는다. 후보에는 작업자 묶음·트리·DAG·실행 명령을 넣지 않으며 원문 인용과 전체 원문 해시를 연결한다. 이 준비 호출과 실패도 비용·시간으로 기록한다.

판단기는 루트 자식 개수, 각 단위의 소속, 자식 유지/추가 분할, 최종 잎 사이의 방향 관계를 고른다. 잎이 실제 다중 파일 구현 작업이 되고 선택한 관계가 선행 산출물 대기·파일 읽기 범위를 바꾼다. 단위·요구사항 소유권은 누락·중복 없이 보존한다. 설명할 때는 **새 후보 목록 안에서 작업 묶음을 재귀적으로 분해**한 것으로 한정한다. Jev가 자유 텍스트로 새 API나 코드를 발명한 실험은 아니다.

루트는 기존 사용자 정책대로 2..가용 단위 수에서 고른다. 비루트는 유지 또는 추가 분할을 고른다. 단일 선택지, 단일 단위, 깊이·용량 경계는 로컬 전이로 별도 기록하며 모델 호출로 세지 않는다. 관계 질문은 방향 A→B/B→A, 의존 없음, 미해결을 구분한다. 현재 그래프에서 불가능한 방향은 후보에서 제외한다. 최대 32개 관계 질문을 한 요청에 묶되 결합 결과의 순환은 전체 commit 전에 거절한다. 임의로 의존 없음으로 바꾸거나 일부만 적용하지 않는다. 미해결·형식 오류·순환은 계획 실패로 남긴다.

질문 상태는 해당 후보의 인터페이스·요구사항과 정확한 원문 인용, 현재 트리/그래프, 전체 원문 해시를 사용한다. 원문이나 선택지를 잘라 한도에 맞추지 않는다. 전체 원문은 준비·작업자·기록에서 유지한다. 양쪽 판단기에 같은 투영 함수를 사용한다.

## 한도와 불확실성

- 후보 최대 30단위, 60산출물, 전체 파일 60개. 잎/논리 작업자 최대 30, 깊이 3, 전체 트리 노드 59, 최종 잎 쌍 435개. 최대치가 목표 개수라는 뜻은 아니다.
- 조건당 판단 요청 최대 128회, 관계 배치 최대 32질문, 요청 최대 240,000바이트. 공식 API 제한은 요청 256,000바이트·64질문·choice 2..255다. 단일 후보는 로컬에서 해소한다.
- Jev 조건당 입력 최대 700,000토큰. 요청 전에 기존 65,536토큰 예약을 더해 한도를 확인한다. 3조건의 상한 합계 2,100,000은 시작 시 기존 장부 잔여 2,366,258 이내다. 누적 입력 10,000,000 장부의 ID·사용량을 유지하고, 매 조건 직전 후속 조건의 남은 상한도 확인한다. 기록된 시작 조회는 7,633,742 사용·pending 0이다.
- 조건당 전체 14,400초 deadline. 개별 작업자 10분 제한은 없다. 실제 구현 재시도와 후보 수리는 구분한다. 공개 검사에 근거한 수리 라운드는 조건당 최대 2회다.
- 자동 전송 재시도 0, 불확실 호출 재전송 0, 모델 fallback 0, 숨김 피드백 기반 수정 0. 외부 응답·정리·journal이 불확실하면 해당 조건을 멈추고 기록을 보존한다. 조건 실패가 예산 장부를 손상하지 않았고 환경이 정상일 때 독립된 다음 조건은 계속한다.

실제 호출은 root만 실행한다. 사전 정상/결함 대조와 소스 일치, 역할별 로컬 검증과 독립 검토, CLI OAuth·고정 Docker 환경·인증된 models GET을 확인한 뒤 시작한다. 등록된 환경/검사/소스 버전은 첫 유료 호출 전에 동결한다. 바뀐 소스로 이어서 측정하면 같은 조건으로 합치지 않는다.

## 수리의 실행과 평가 경계

파일 준비 검사는 문법·산출물 무결성을 확인한다. 완성 후보는 공개 7개 suite/85개 검사를 모두 실행하고, 알려진 한 suite 실패 때문에 나머지 suite를 생략하지 않는다. 알려진 설치·초기화 실패는 실패로, 불확실 프로세스·정리·변조된 보고서는 불확실로 구분한다. 실행되지 않은 case를 성공으로 세지 않는다.

공개 실패 묶음과 정확한 산출물 revision을 수리 판단에 전달한다. 실행기가 제공하는 중복 제거된 선택지는 실패 소유 범위, 소유 범위와 후속 소비자, 전체 잎, 중단이다. 선택된 범위가 새 라운드의 실제 Claude 작업을 호출한다. 이전 후보와 journal은 불변으로 남기고 미변경 산출물은 복사·재검증한다. 모든 완성 라운드는 전체 공개 검사를 다시 실행한다. 공개 성공 후에만 수리가 멈추는 것은 아니며 모델의 중단 선택/한도 소진도 원본대로 남긴다.

최종 후보는 별도 원본 grader로 평가한다. 숨김 검사 내용과 세부 실패를 계획·구현·수리로 반환하지 않는다. 독립 평가 63개 전부 통과하고 skip/누락이 없을 때만 제품 완료로 인정한다. 실패 시도에도 시간·토큰·비용은 모두 남기고 성공 완료시간은 `null`로 둔다.

## 측정과 가격

주 비교는 공통 후보 준비 **전체** 시간·비용 + 조건별 사전 검사·판단·구현·수리·공개 검증·정리까지의 wall/사용량이다. 후보 준비는 실제 cohort에서 한 번 발생하므로 실제 총지출에는 한 번만 더한다. 4분의 1 배분 수치는 보조 열로만 제공한다. 독립 채점과 별도 Opus 모니터는 각각 별도 구간/비용이며 필요하면 평가 포함 총시간도 함께 표시한다. 공급자 호출 시간 합과 병렬 경과시간을 혼동하지 않는다.

판단 단계별 호출·선택·요청/응답·입력/출력/캐시 생성/캐시 읽기·모델 응답 ID·HTTP/CLI wall, 트리 깊이·잎 수·선택된 간선·실제 동시 실행·critical path, 각 수리의 실패 case·선택 범위·재실행 수·최종 공개/독립 품질을 기록한다. 측정하지 않은 잠재 최적 실행시간은 추정하지 않는다. 완료한 조건끼리만 완료시간 감소율을 계산한다. 실패 조건은 실패까지의 시도시간과 품질·비용으로 비교한다.
