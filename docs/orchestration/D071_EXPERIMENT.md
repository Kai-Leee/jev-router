# D071 — 원인 연결 수리와 작업자 프로필 선택

상태: 구현·사전 검증 중. 새 실행 결과 미측정.

## 사용자 요청과 가설

추가 description 실패를 잡는 공개 검사와 producer→IR→renderer 담당 연결을 수정한다. Jev가 실제 허용 model/effort 중 작업별 프로필을 선택해 실행하도록 연결한다. 동일 품질을 유지하면서 Claude만 판단하는 기준선 대비 전체 완료시간과 공식 환산비용을 낮출 수 있는지 측정한다.

## 예정 조건

동일 원문·catalog·공개 검사 버전·Docker image·실행 슬롯에서 각1회 새 개발을 비교한다. 구조·검사 준비 완료 후 정확한 실행 manifest와 source pin을 고정한다.

1. `claude_all`: 반복 분해·관계·수리 판단 Claude, 작업자 Opus5.5 medium 고정.
2. `jev_all`: 반복 판단 Jev, 작업자 Opus5.5 medium 고정.
3. `jev_profile`: 반복 판단 Jev, 작업별 model/effort도 Jev가 선택.

조건2는 모델·effort 변경 효과를 조건1과의 판단자 변경 효과에서 분리하기 위한 대조다. 이 Claude 기준선은 동일 구조의 Claude-only 판단/작업자 조건이며 단일 무제약 Claude 세션과 같다고 부르지 않는다. 원래 D067 Claude 결과도 과거 참고값으로 별도 보존한다.

새 개발에서 해당 실패가 재현되지 않을 수 있으므로 D070의 보존된 실패 후보를 새 디렉터리에 복사해 추가 공개 진단 실패를 재현하고 실제 Jev 수리를 별도 측정한다. 이 수리 시간·비용은 처음부터 개발한 결과에 합치지 않는다. 과거 후보를 직접 고치지 않는다.

## 평가 경계

원래 공개85개·독립63개와 추가 공개description8개를 구분하며 신규 성공은 새 공개 기준과 독립 채점을 모두 만족해야 한다. 공개 요구사항·원문은 양쪽에 동일하게 주고 숨김 검사는 입력하지 않는다. 과거85/85 결과를 새 점수로 덮지 않는다.

총 시간은 arm 시작→공개 결과와 arm 시작→독립 채점 종료를 함께 기록한다. 실패 종료시간을 완료 가속률로 계산하지 않는다. Jev POST, Claude CLI, 프로필 선택, 로컬 singleton, 재시도·미사용/캐시 토큰, 별도 모니터를 분리한다. 선택 모델/effort와 실제 실행 인자·모델 identity를 연결한다. 일회 관측으로 일반 최적 프로필이나 인과효과를 확정하지 않는다.

## 예산·보존·권한

D067 이후 사용자가 승인한 조건별/누적 토큰 무상한 정책을 유지한다. 기존 장부를 초기화하지 않으며 잔액·불확실 정산·서비스 입력 제한은 유지한다. 자동 불확실 POST 재시도는0이다. 새로운 실행은 이번 사용자 지시로 승인됐고 root가 실행한다. 구현 담당은 provider 호출을 하지 않는다.

실행 전 기존 결과·후보·현재 소스를 snapshot/hash로 보존하고 root가 source freeze 후 실행한다. 실제 모델 가용성·가격·CLI/OAuth·Docker·입력 한도를 사전에 확인한다. 실험 도중 소스를 바꾸거나 실패한 원본을 이어 쓰지 않는다.

역할: [D071_PARALLEL](../agents/D071_PARALLEL.md). 구현·결과·남은 일은 이후 새 기록으로 갱신한다.

## 실행 전 발견과 입력 표현 정정

`benchmark-runs/d071-public-candidate-recheck-01`에서 기존 D070 후보를 읽기 전용으로 새 공개 검사에 연결했다. 실제93개 중 기존85개는 통과하고 description8개는 실패했다. 전후38파일 snapshot이 같으며 모델 호출은0이다. 이는 실제 재수리에 사용할 실패 근거이고, 수리 완료 증거는 아니다.

초기 profile 질문은 코드용 질문 ID만 다르고 본문이 같아 작업을 구분하지 못하는 결함이 있었다. 고정 질문 본문에 task/worker/수정 artifact와 경로를 넣었다. 수정 전후 원본과 독립 검토는 `benchmark-runs/d071-review-01/question-target-{before,after}.json`에 보존한다.

24,000B는 D069의 내부 수리 운영 기준이다. 70,510B 요청이 토큰 추정 검사를 통과하고도 실제 HTTP400 model_input_limit으로 거부됐던 결과에 대응해 선택한 값이며, provider의 공식 바이트 제한이 아니다. D071 사전 검사에서 첫 수리23,909B와 이전 수리 기록 포함25,948B가 나와 이를 맞추려고 dictionary/fragment codec을 만들었으나, 코드의 무손실 복원이 Jev의 의미 해석을 입증하지 못한다. **실제 D071에서는 이 codec을 사용하지 않고 읽을 수 있는 JSON을 전송한다.** 압축 시도와 실패한 입력 크기 검사는 삭제하지 않는다.

수리 판단기에는 실패 assertion/원인 경로에 연결된 요구사항 원문과 실패·이전 수리 이력·법적 후보를 유지한다. 나머지 구현 요구사항은 작업자 전체 입력 및 controller 원본/omission 증거에 보존한다. 연결이 불명확하면 해당 요구사항을 유지한다. 모든 새 조건은 같은 표현을 사용한다.

V3에만48,000B 운영 기준을 명시한다. 기존V1/V2 원본과 문항32,000/전체64,000 **토큰 추정** 기준은 유지한다. 새 바이트 기준은 수용률이 검증된 cutoff가 아니며 추정 통과도 실제 provider 수락을 보장하지 않는다. 실제 v4 실패·1회 수리 이력·현재 profile 메타데이터를 포함한 요청 전체 직렬화를 재검사한 뒤 소스를 고정한다. 프로필 질문도 같은 추정기의 한계를 가지므로 큰 배치의 추정 통과를 실제 수용으로 보고하지 않는다.

최종 프로필 preview06은58/58요청이 추정 검사를 통과했다. 현재 source로 요청/metadata를 다시 만든 결과도58/58동일하며 최대47,659B다. 합성20프로필 집계는 입력 경계 검사이고 실제 선택·성능 데이터가 아니다. 동일한 기존5개 입력 조건의 배치는14→25회로 늘었으므로 호출 수 감소를 주장하지 않는다.

전체 `npm test`는1190/1190통과·실패/skip/cancel0,40.424초였다. Root 집계 helper가 TAP `#` 요약만 예상하고 Node spec reporter `ℹ`를 놓쳐 첫 summary에 null을 기록한 자체 결함을 발견했다. npm은exit0이며 원본 log/summary를 보존하고 `reconcile-regression.mjs`로 `regression-summary-02.json`만 추가했다. 테스트 재실행은0이다. 독립 집중 검사는91/91통과했다.
