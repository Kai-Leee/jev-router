# D055 — 작업·테스트 목록을 이용한 반복 분할

확인일: 2026-10-10. 상태: 설계와 질문 초안. 실행기 구현·실제 Jev 호출·효율 측정 전.

사용자 방향은 필요한 분리를 Jev가 판단하고, 작업과 테스트 목록을 분리해 전달하며, 적절한 단계에 도달할 때까지 분할을 반복하는 것이다. 아래 구체적 필드와 종료 규칙은 이 방향을 구현하기 위한 제안이며, 측정으로 확정한 최적 정책이 아니다. D053의 실행 원본은 바꾸지 않는다.

## 현재 구조에서 달라지는 점

D053은 소유자 없는 파일 목록을 한 번 배정하는 방식이다. 새 방식은 공개 요구사항의 행동 단위를 반복해서 배정한다. 파일 하나가 여러 행동에 관여해도 논리적으로 나눌 수 있으나, 같은 파일을 동시에 수정할 수 있다는 뜻은 아니다. 작업 트리는 분해 이력이며 실행 순서는 별도의 의존 그래프로 관리한다.

외부 계획 산출물은 `tasks.json`과 `tests.json` 두 목록을 기본으로 한다. 공통 목적·원문·인터페이스·금지사항은 한 번 저장한 명세를 참조한다. 작업자에게는 두 목록의 관련 항목과 실제 명세 발췌를 조립해 전달한다. Jev가 로컬 문서 경로만 보고 내용을 읽을 수 있다고 가정하지 않는다. 판단 로그·비용·버전 정보는 별도 장부에 보존한다.

## 목록 계약

- 작업: `id`, `parent_id`, `goal`, `requirement_refs`, `inputs`, `outputs`, `depends_on`, `test_ids`, `write_scope`, `planning_status`.
- 테스트: `id`, `requirement_refs`, `scenario`, `input`, `expected`, `scope`, `task_ids`, `runner_ref`, `status`.
- `scope`는 단위·통합·전체 동작을 구분한다. `task_ids`는 하나 이상이며 통합 테스트를 억지로 한 자식에게만 배정하지 않는다.
- `runner_ref`가 없으면 테스트 명세만 존재한다. 테스트 코드·실행·통과를 주장하지 않으며 초기 실행 상태는 `not_run`이다.
- 원문에서 구분된 최소 의무 단위마다 하나의 책임 leaf를 두고, 다른 기여 작업은 연결로 남긴다. 한 R번호가 여러 하위 의무로 나뉘면 원문 구간과 하위 ID를 보존한다. 서로 다른 작업이 같은 R번호를 참조하는 것은 중복 실행과 다르다.
- 부모를 분할하면 부모는 집계 노드가 되고 실행 대상에서 제외한다. 자식 결과가 통합되기 전에는 부모 요구사항을 충족했다고 표시하지 않는다.

## Jev와 문장 생성의 경계

공식 문서의 systemone API는 `choice`, `noul`, `score` 형태로 답한다. 임의의 하위 작업·테스트 코드를 자유 서술로 생성한다고 가정하지 않는다. 원문의 항목·조건·예시를 출처가 있는 행동/검증 단위로 준비하고 Jev가 개수, 기준 단위, 나머지 단위의 배정을 고른다. 코드가 선택된 원문을 템플릿에 붙여 작업 설명과 테스트 명세를 조립한다.

원문만으로 입출력·예상값을 만들 수 없으면 `needs_spec`로 남긴다. 새로운 설명이 필요한 경우의 Claude 보조 생성은 별도 준비 단계로 기록하고 비용에 포함한다. 반복마다 Claude가 전체 계획을 다시 쓰게 하지 않는다. 이 보조 생성의 사용 조건은 아직 구현되지 않았다.

출처: [Jev API 문서](https://jev-ai.pro/docs#question-types), 2026-10-10 웹 문서 확인. 문서상 API 형태 확인이며 이번 설계의 실호출 호환성 검증이 아니다.

## 분할 루프

1. 현재 leaf 중 명세와 검증 조건이 준비된 노드만 판단 대상으로 고른다. 이미 검토한 동일 내용·명세·인터페이스·질문 버전은 재호출하지 않는다.
2. Jev에 해당 노드, 관련 테스트, 필요한 공통 제약·선행 인터페이스·자원 조건을 전달한다. 완료 코드와 관계없는 형제의 전체 원문을 매번 복제하지 않는다. 근거가 부족하면 줄였다는 이유로 생략을 정당화하지 않고 명시적 gap을 기록한다.
3. 기존 숫자 선택을 노드별로 적용한다: `1`은 현재 단위 유지, `2..5`는 그 개수의 자식 생성. 전역 작업 수가 5개로 제한된다는 뜻은 아니다. 동시 실행 수는 별도 정책이다.
4. 분할이면 Jev가 서로 다른 행동 단위를 자식의 기준점으로 선택하고, 남은 단위를 순차 배정한다. 이미 확정한 배정과 알려진 의존 관계를 유지하며 불가능한 배정은 코드가 제외한다. D052처럼 독립 배정들을 마지막에 합쳐 충돌시키는 방식을 반복하지 않는다.
5. 테스트를 연결한다. 한 자식 내부에서 확인할 테스트는 그 자식에, 여러 자식이 필요한 테스트는 통합 범위에 남긴다. 원래의 전체 동작 테스트를 삭제하거나 완화하지 않는다.
6. 자식 의무의 합집합이 부모 의무를 보존하는지, 실제로 작아졌는지, 빈 작업·순환 의존·중복 쓰기가 생겼는지 검사한다. 실패한 수정안은 이전 유효 계획에 반영하지 않는다.
7. 유효한 자식만 다음 라운드에 넣는다. 모든 leaf가 준비되었거나, 구체적인 gap/보호 한도로 진행할 수 없으면 계획 루프를 종료한다. 종료 사유를 실행 가능 상태와 구분한다.

같은 부모 전체를 복제한 자식, 제목만 바꾼 자식, 원문 의무가 하나도 줄지 않은 자식은 진행으로 인정하지 않는다. 반복 계획 해시와 한도 도달은 종료 사유이지 작업이 충분히 작다는 증거가 아니다. 최대 깊이·총 leaf 수·판단/수정 횟수·계획 토큰 한도는 실행 manifest에 명시해야 하며 이번 문서에서 임의 최적값을 정하지 않는다. 기존 누적 10M 장부와 결과 불확실 요청의 재전송 금지는 유지한다.

## 더 나누지 않을 조건

Jev의 `1`은 다음 조건을 만족하는 단위 유지 선택으로 정의한다.

- 하나의 일관된 결과와 명확한 입출력이 있다.
- 원문과 연결된 검증 조건이 있고 필요한 외부 선행 조건이 드러나 있다.
- 더 나누면 별도 검증 가능한 결과나 실제 병렬 구간을 얻기보다 전달·통합 작업을 늘린다.
- 작업자가 다시 큰 설계 결정을 해야 하는 미해결 gap이 없다.

코드는 참조·의존·쓰기 충돌 등 구조 조건을 검사한다. Jev의 적절성 선택과 구조 검사는 실제 구현 정확도나 예상 시간 단축의 증거가 아니다. 정보 부족, 실행 가능한 테스트 부재, 범위 충돌을 `1`로 숨겨 실행하지 않는다. 테스트 명세만 있는 단계에서는 계획 준비와 검증기 실행 준비를 별도로 표시한다.

같은 파일의 서로 다른 기능을 나눴다면 초기 구현에서는 파일 단위 쓰기 잠금으로 순차 실행하고 최신 선행 산출물을 읽는다. 병렬 쓰기가 필요하면 독립 파일로의 경계 변경 또는 패치 통합 작업을 별도 계획해야 한다. 이 추가 설계·통합 비용도 측정한다.

## 설명용 예시 — 실행된 Jev 결과가 아님

현재 R14의 기본값 처리 요구사항은 숫자 문자열 변환, 불리언 문자열 변환, 날짜/시간/UUID 변환, enum 참조 기본값처럼 행동 단위로 표현할 수 있다. Jev가 어떤 단위들을 함께 둘지 고르며 아래 사례를 고정 분할로 주입하지 않는다.

- 작업 예: 정수·실수 기본값 변환. 연결 테스트 예: 문자열 `"4"`는 정수 `4`, `"5.5"`는 실수 `5.5`로 생성된다.
- 작업 예: 불리언 기본값 변환. 연결 테스트 예: `"False"`/`"false"`는 `False`이며 값과 Python 타입을 확인한다.
- 부모 통합 테스트 예: 원문 요구사항을 담은 OpenAPI 문서로 클라이언트를 생성하고 import한 뒤, 기본 인자로 만든 모델의 값과 타입을 확인한다.

예상값은 공개 명세 R14에서 가져온다. 예시 테스트 코드를 작성하거나 실행하지 않았으며 전체 R14를 이 세 항목으로 대체하지 않는다. 기존 파일 경계가 같다면 이 예시 작업들의 동시 쓰기는 허용하지 않는다.

## 검증과 비교 계획

먼저 무과금 구조 검증으로 의무 누락, 테스트 연결 누락, 빈/동일 자식, 부모·자식 중복 실행, 순환, 공유 파일 충돌, 반복 계획, 한도 도달, 통합 테스트 보존을 확인한다. 테스트 ID 존재만으로 의미상 검증 범위가 충분하다고 판정하지 않는다. 의도적으로 잘못된 동작을 넣었을 때 실제 테스트가 잡는지도 이후 확인한다.

현재 한 번 배정 방식과 재귀 방식에 같은 공개 목표·독립 평가·작업자 프로필을 적용한다. 준비/분할/구현/통합/수정/평가 시간, 호출과 토큰, 완료율, 최대 경로 시간, 실제 병렬 구간을 모두 기록한다. 테스트 준비 비용을 재귀 방식에서 공짜로 처리하지 않는다. 현재 HTTP400 원인 진단과 응답 본문 보존 문제는 재귀 분할과 별도로 남아 있으며, 이 설계가 그것을 해결했다고 주장하지 않는다.

다음 구현 범위는 두 목록의 스키마와 검사기, 사전 질문 로더, 진행을 보장하는 분할 루프다. 이번 변경은 설계·질문 초안·기록만 추가한다. 실제 루프 연결, 새 모델 호출, 추가 benchmark, 원본 Personal OS 변경, 커밋/푸시는 하지 않았다.
