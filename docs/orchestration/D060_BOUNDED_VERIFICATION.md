# D060 — 작업량 상한, 독립성 질문, 실행 검증 게이트

사용자가 D059 후속으로 수락한 방향: 공유 파일·의존 관계·첫 작업자 쏠림을 배정 질문에 넣고, 실제 공개 검증 결과를 받은 뒤 후속 작업을 연다. 과도한 작업자1의 배정도 줄인다. 이번에는 별도 v2 모듈과 연결 경로를 구현하고 로컬 검증했다. **D059 원본과 기존 유료 실행기는 변경하지 않았다. D060 유료 제품 재실행은 하지 않았다.**

## 질문과 상한

질문 정본은 [sequential-allocation.v2.json](contracts/sequential-allocation.v2.json), 구현은 [sequential-allocation-v2.mjs](../../src/orchestration/sequential-allocation-v2.mjs)다. 컨트롤러가 이 파일의 영어 문장을 읽고 값만 채운다. Claude/Codex가 별도로 질문을 다시 생성하는 흐름은 없다.

- 개수 선택부터 공유 쓰기 경로, 명시된 의존 관계, 의존 관계 미확정 ID를 전달한다.
- 배정·재배정 질문에 기존 담당자와 경로, 현재 배정 수, 최소·최대, 후속 작업자에 필요한 용량을 전달한다.
- 임시 상한은 `ceil(1.25 × 전체 의무 수 / 작업자 수)`다. 80개·3명이면34개다. 모든 작업자에게 적용하며 최적값으로 확정한 것은 아니다.
- 최소 배정은 `max(1, 남은 의무 − 후속 작업자 수 × 상한)`이다. 앞 작업자를 줄인 부담을 마지막 작업자에게 전부 넘기지 않는다.
- 범위를 벗어나면 거부한 선택을 기록하고 Jev에 남은 후보 전체를 다시 선택하도록 요청한다. 최대3회 재배정 후에도 실패하면 중단한다. 조용히 자르거나 요구사항을 버리지 않는다. API 오류/불확실한 결과의 재시도와 이 유효 응답의 재배정은 다르다.
- 모델·노력도 선택은 전체 배정 및 DAG 검사 뒤에 한다. 선택지가1개면 API를 부르지 않고 결정론적 처리라고 기록한다.

이 상한은 **의무 개수**만 제한한다. 원문 요구사항을 요약·삭제하거나 전체 프롬프트 토큰을34/65로 줄였다는 뜻이 아니다. 의무마다 난이도가 달라 시간·비용 균등화도 보장하지 않는다. 파일이 겹치면 계속 직렬화한다.

## 연결 API와 검증 경계

[bounded-verified-workflow.mjs](../../src/orchestration/bounded-verified-workflow.mjs)의 `runBoundedVerifiedWorkflow`는 다음 순서다.

1. 입력·실행 콜백·허용 경로·동시성·공개 검사 매핑을 확인한다. 누락된 검사 매핑은 유료 계획 호출 전 `PUBLIC_CHECK_MAPPING_MISSING`으로 차단한다.
2. v2배정 → 기존 순수 실행-envelope 검증 → 작업자 실행을 연결한다.
3. 신뢰하는 컨트롤러가 해당 후보 revision을 읽고 공개 검사를 실행한다.
4. 모든 배정 test ID에 실행/통과/종료코드0/check ID/동일revision 증거가 있는지 검사한다. 후보가 검사 도중 바뀌어도 거부한다.
5. 통과한 작업자만 완료 목록에 추가하여 후속 작업을 연다. 실패·불확실한 실행 반환도 검증 전에 거부한다. 이미 실행 중인 독립 작업은 마무리하되 새 작업 발행은 중단한다.

[public-check-registry.mjs](../../src/orchestration/public-check-registry.mjs)는 문서 test ID와 컨트롤러 소유 실행 검사를 연결한다. 작업자 자기보고의 `passed:true`를 입력으로 쓰면 안 된다. `runner_ref` 문자열 존재는 실행파일·검사 적절성의 증거가 아니다. 실제 검사 adapter는 subprocess/격리 실행 결과와 양수 어설션 수,0skip을 반환해야 한다. 모든 관련 체크가 통과해야 해당 test ID를 통과시킨다.

## 실행한 검증

`node scripts/bounded-verified-preflight.mjs`로 무과금 재현한다. [저장 결과](../../benchmark-runs/d060-preflight/result.json)는 공개80의무/85테스트와 **모의 응답**을 사용한다. 최초65개 선택을 명시적으로 거부한 뒤27/27/26,상한34로 배정했다.80개 단일소유권과85개 테스트 연결을 유지했다. 모의 질문12개 요청의 codec 왕복복원이 모두 일치했고 최대전송127179bytes였다. 실제 모델 입력 한도 통과·이해도·토큰 감소를 검증한 값은 아니다. 이 배정에도 파일 충돌이 있어1→2→3 순서가 남았다.

실제 로컬 subprocess 어설션이 실패하면 후속 작업자가 실행되지 않고, 통과하면 실행되는 것을 테스트했다. 누락·중복·추가ID·stale revision·skip·0assertion·실행실패·불확실성도 검사했다. 이는 작은 합성 입력에 대한 실행 메커니즘 검증이며 실제 제품 개발·독립63채점이 아니다.

최종 `npm test`: **799/799통과**, 실패·skip0,11311.556625ms. [로그](../../benchmark-runs/d060-preflight/regression-final.log). 초기785개 회귀도 보존했다. 중간 로컬 연결 테스트2건은 fixture의schema_version 누락으로 실패했으며 fixture를 수정했다. 리뷰에서 발견한 계획 전 콜백 설정 검사 누락과 실패 상태 반환 허용도 수정 후 회귀했다. [독립 리뷰](../agents/D060_REVIEW.md).

## 실제 제품 재실행 전에 남은 연결

현재85개 공개 테스트 명세의 `runner_ref`는 모두null이다. 기존 smoke 일부 통과를85개 전체 통과로 변환하지 않았다. 새 workflow의 실제 명세 사전검사는85개 매핑 누락을 발견하여 계획/작업자 콜백0회로 차단했다.

또한 여러 작업자를 참조하는 통합·E2E 검사는 후속 구현 전 첫 작업자에게 요구하면 진행이 막힐 수 있다. 제품용 검사 목록에는 **작업자 단위로 실행 가능한 경계 검사와 후속 구현을 기다리는 통합 검사**, 필요한 파일/선행 단계, 각 공개 명세와의 대응을 명시해야 한다. 그 검사 구현·매핑·준비조건 설계는 아직 완료하지 않았다. 현재 게이트의 엄격한 전체 test ID 조건을 무시하거나 미실행을 통과로 바꾸지 않는다.

새 workflow는 콜백 API와 무과금 preflight로 연결됐다. 기존 D059 유료 CLI의 기본 동작을 바꾼 것은 아니며 새로운 유료 실험에는 기존 장부/계측 adapter와 검사 준비조건 연결이 추가로 필요하다. 따라서 이번 결과로 실제 Jev가27/27/26을 골랐다거나 개발이 빨라졌다고 하지 않는다.

유료 Jev/Claude 호출0,장부 변경0. 기존 PersonalOS/Vault·D059후보·컨테이너·커밋·푸시 변경은 없다. 새 코드·질문 계약·테스트·문서·로컬 검증 자료는 미커밋으로 남겼다.
