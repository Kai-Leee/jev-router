## 고정 검사가 놓친 품질 회귀

새 A는 84/85 → 첫 수리 뒤 84/85 → 두 번째 수리 뒤 85/85였다. 그러나 기존 fixture는 requestBody 설명과 schema/model 설명이 같은 문장이라 출처 혼동을 구별하지 못했다. 설명을 다르게 하거나 schema 설명을 없앤 공개 진단을 세 후보에 동일하게 실행했다. 각 조건의 sync/async 등 네 함수, 총 8 assertion에서 **새 A 0/8, Claude 8/8, D069 8/8**이었다. 이 추가 진단은 원래 148개 검사에 사후 합산하지 않는다.

[품질 검토](D070_QUALITY_REVIEW.md)는 원시 수리 요청·답변·수정 파일·추가 실행을 연결한다. 앞단 operations가 requestBody 설명을 BodyIR에 넘기지 않았고, 두 번째 수리는 template에서 모델 설명으로 대신 채웠다. 특정 정답 문장 하드코딩은 발견되지 않았다. 두 번의 Jev 수리 선택지에는 A19 template 담당 수리와 중단만 있었으며 앞단 producer/IR/generator 담당은 없었다. 작업자의 좁은 읽기·쓰기 범위와 실행기가 만든 후보 목록이 근본 수리를 막았다.

후속으로 필요한 것은 **실패 assertion → 값의 producer → IR → renderer 연결을 수리 후보·읽기 범위에 포함**, 반복 실패 시 실제 수정과 남은 실패를 다음 질문에 전달, 서로 다른 설명 출처를 구별하는 공개 경계 검사다. 전원 재호출이나 단순 worker 수 증가로 대체하지 않는다. 이 후속 수정·새 유료 실험은 미실행이다.
