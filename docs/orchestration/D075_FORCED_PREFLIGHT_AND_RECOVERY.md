# D075 — 전송 전 강제 검사와 근거 기반 복구

2026-10-12. 상태: 병렬 구현·실측 종료, 제품 미완료. 첫 실행은 profiles HTTP400으로 수리 작업자 이전에 중단됐다. 전달/후보 보존 수정 후 두 번째는 공개88/93·독립60/63, 후속 owner HTTP400 및 CANONICAL_INPUT_ALREADY_APPLIED로 종료됐다. [결과 기록](D075_RESULTS.md)에 두 실행과 시간·토큰·공식 환산 비교를 보존한다.

## 목적과 비교 조건

사용자는 D074 검사를 실제 Jev 전송 전에 강제 연결하고, 실패 복구 루프를 병렬 구현한 후 보존된 실패 후보를 재실행하도록 요청했다. 목표는 Claude 단독 대비 개발 완료 시간과 단가 감소다. 이번 조건은 새 개발 전체가 아니라 보존 후보의 증분 수리다.

- 주 비교의 출발점은 `benchmark-runs/d073-comparison-01/jev_profile`이다. 이전 `d073-focused-new-02` 수리도 같은 출발 후보를 사용했다. 출발 공개 검사는 79/93이다.
- 이전 수리 결과는 공개 91/93, 독립 61/63이며 미완료다. 이 후보에서 별도 실행한다면 다른 출발 상태를 가진 증분 조건으로 표시한다.
- 과거 후보·결과·요청·회계 영수증은 읽기 전용으로 보존한다. 새 실행은 `benchmark-runs/d075-*`의 새로운 경로만 사용한다. 실행 전후 파일 해시를 비교한다.
- 요청, 초기 카탈로그, 검사 목록, Docker 이미지와 평가 경계를 고정한다. 숨김 검사 내용은 복구 입력으로 사용하지 않는다.
- 토큰/장부 상한은 null이다. 공식 요청 제한, 권한, 결과 불확실·미정산 및 무진전 방지는 유지한다. 같은 요청의 SDK 자동 재시도는 0이다.

## 전송 경계

공식 문서는 2026-10-12 다시 확인했다: [Jev API](https://jev-ai.pro/docs#official-sdk), [실패 처리](https://jev-ai.pro/docs#errors). 공개 API 검사는 256000바이트·최대64질문을 제한하며 모델 자체 문맥 제한은 별도다. 결과가 불확실한 POST는 자동 재전송하지 않고 상태를 먼저 확인한다. 이 규칙은 사전 검사 통과와 실제 모델 수락을 분리하는 근거다.

새 `adaptive-dag-comparison/v10` manifest가 강제 검사를 선택한다. 보존 수리 CLI의 기본 manifest를 v10으로 변경하고, 명시한 과거 manifest는 역사적 재현에 남긴다.

검사는 정확한 직렬화 요청, 정책 해시, 소스 핀, 대상 URL·모델을 대조한다. 예약 직전 차단은 예약 0/POST 0이다. 예약 뒤 전송 직전 소스·요청이 바뀐 경우에는 POST 0과 실제 예약 상태를 별도로 남긴다. 이 두 경우를 같은 회계 상태로 합치지 않는다.

모든 단계에서 형식·공식 바이트 제한·대상·해시를 검사한다. `repair_owners/inferred-v2`는 고정 질문과 공개 근거 연결도 검사한다. 다른 단계의 의미 검증을 수행한 것처럼 표시하지 않는다. 로컬 검사를 통과해도 공급자의 정확한 토큰 계산과 모델 문맥 수락, 답변 품질은 보장하지 않는다.

입력 축소는 담당 추론의 build→infer→apply→validate와 실제 전송이 동일 요청 해시를 공유하도록 opt-in projector로 연결한다. D074 정책 v1은 보존하고 새 소스는 정책 v2로 고정한다. 현재 코드에서 역사적 v1 검사 시 SOURCE_DRIFT가 발생하는 것은 새 정책을 적용한 통과 결과가 아니다.

입력 표현은 두 수준을 구별한다. 같은 값의 inline 공유는 정확 복원 가능한 표현 변경이다. 별도 relevance projection은 실제 같은 revision에서 passed+resolved이고 현재 실패 요구사항/원인 관련 경로와 무관함이 확인된 과거 상세 관측만 요약하는 의도적 선별이다. 후자는 lossless가 아니다. 현재 실패·unknown·미실행·관련 또는 관계 불명인 근거는 원문을 유지하고, 요약된 관측의 ID·이전 오류·현재 상태와 전체 공개 검사 coverage/counts는 남긴다. 제거 필드·근거·원문 해시는 controller 보고서에 보존한다. 새 소스 근거로 관계가 생기면 원문을 다시 포함해야 한다.

오프라인 입력 재생 중, 새 원인 조사 소스 전체를 owner 입력에 추가하면 축소 효과가 뒤집히는 것을 발견했다. 최종 단계별 전달에서는 owner에 실제 import·공개 함수 signature·선택 산출물/의존 관계의 경계 관측을 넣고, 수리 chooser와 worker에는 관련 source ranges를 전달한다. owner가 전달받지 않은 함수 본문까지 읽었다고 주장하지 않는다. 각 단계의 실제 본문·바이트·SHA와 원문 보존 보고서를 별도로 확인한다.

## 실패 복구 경계

복구는 현재 종료 원인과 검증된 근거에 따라 다음 행동을 정한다. 과거 실패는 이력이며 현재 실패로 자동 재활성화하지 않는다.

1. 결과 불확실·미정산: 요청 결과와 회계를 확인하기 전 POST/작업자를 재호출하지 않는다.
2. 입력 부적합·문맥 초과: 지원하는 owner/repair 경로에서 기존 근거·선택지·권한을 유지한 새 입력과 변경 해시를 만들고 강제 검사한다. 같은 canonical 표현을 이미 썼으면 CANONICAL_INPUT_ALREADY_APPLIED로 중단한다. profile 자동 입력 재구성은 미지원이며 모든 문맥 실패를 자동 해결하는 루프가 아니다.
3. 검사 환경/오래된 근거: 환경과 후보 버전 연결을 복원하고 다시 검사한다.
4. 일부 개선: 현재 남은 실패를 기존 담당 추론→수리 선택→모델/노력도→작업자 경로로 보낸다.
5. 무변경·무진전: 새 관련 소스 근거와 변경된 수리 입력/범위가 확인되기 전 동일 작업자를 재호출하지 않는다. 모델/노력도 변경만으로 재호출 자격을 만들지 않는다.
6. 공개 검사 통과: 같은 후보 버전을 독립 채점한 후 완료 여부를 판정한다. 공개 검사만으로 완료라고 쓰지 않는다.

병렬 소유권과 구현 파일은 [D075 역할 기록](../agents/D075_PARALLEL.md)에 있다. 기존 D074 설계·오프라인 증거는 [D074 기록](D074_PROMPTING_AND_FAILURE_LOOP.md)에 남는다.

무진전은 전체 실패 수만 보지 않는다. 직전 D073에서 A14/A15의 개선과 A10의 무변경이 동시에 발생했다. 남은 실패와 선택했으나 바뀌지 않은 산출물이 있으면 `repair_remaining_scope_no_change → inspect_no_write_cause`로 새 근거 수집을 요구한다. 이를 A10이 실제 원인이라는 확정 판정으로 사용하지 않는다.

## 측정 계약

- 성공 완료 시간과 실패까지의 시간을 구분한다. 미완료가 더 빨리 멈춘 것을 완료 속도 개선으로 계산하지 않는다.
- runner 단조 시계 시간, 독립 채점 시간, 실제 wall-clock 간격을 별도 기록한다.
- Jev POST, Claude CLI/작업자 호출, 재사용된 산출물과 새 호출을 따로 센다.
- 토큰은 입력·출력·캐시 쓰기·캐시 읽기 분모를 표시한다. 실패 요청의 누락 사용량은 null/unknown으로 남긴다.
- 공식 요금으로 계산한 API 환산액과 실제 청구/월 구독 배분액을 구분한다. 실제 청구 근거가 없으면 null이다.
- 모니터 호출은 개발 수리 비용과 별도 집계한다. 원본 보존과 새 컨테이너 정리도 종료 시 확인한다.

## 현재 증거 수준

구현·집중 검사·실제 수리·독립 채점은 각각의 단계로 기록한다. 첫 실행 `benchmark-runs/d075-same-source-01`은 원본 실패를 재현한 뒤 Jev 3회, Claude 수리 0회에서 멈췄다. 첫 두 Jev 판단은 성공했으나 profiles 입력 149079B가 모델 문맥 제한으로 거부됐다. 원결과·실제 wire·검사 영수증은 보존했다.

병렬 개발 도중 독립 검토는 같은 소스 줄의 순서/범위 표현만 바꿔 새 근거로 인정시키는 우회와 callback 공유 참조 변조를 발견했다. 최초 재현을 보존하고, 파일·revision·SHA·줄 coverage 정규화 및 callback 사본 격리로 수정했다. 수정 전후 검증은 `benchmark-runs/d075-review-01/` 및 `benchmark-runs/d075-recovery-01/`에 있다.

첫 live 실행은 오프라인 검사가 보지 못한 추가 경로를 드러냈다. `inferred_ownership.repair_input_context`의 controller 검증용 88334B가 profile 입력에 복제됐다. 과거 같은 task의 성공 profile 60491B와 같은 요구/선택지인데 wire는 149079B로 늘었다. profile projection에서 controller 근거를 참조/해시로 남기는 경계를 고쳤고, 실제 두 번째 입력60721B는 수락됐다. 작업자 어댑터의 합성 전달 검사만으로 profile 생성 경로까지 검증했다고 볼 수 없었다.

또한 profiles 준비 실패는 runtime/수리 작업자 실행 전이지만 첫 실행은 이를 수리 round로 세고 마지막 완전한 round0 export의 최종 포인터를 놓쳤다. 후보 38파일은 사라지지 않았고 독립 감사 후 별도로 채점했다(공개79/93·독립60/63). 원결과를 고치지 않고 후속 executor에서 준비 실패와 실제 실행을 분리했다. profiles의 자동 입력 재구성/재전송은 아직 지원하지 않으며 미정산·결과 불확실 때 재호출하지 않는다. 지원하지 않는 분기는 명시적인 blocked 기록으로 남긴다.
