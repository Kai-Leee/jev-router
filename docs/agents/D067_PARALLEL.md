# D067 — 토큰 상한 해제와 병렬 재실험 역할

2026-10-11 KST. 최신 사용자는 조건별 상한과 장부 토큰 한도를 현재 해제하고 즉시 병렬 실행하도록 명시했다. D066의 700,000/10,000,000 한도를 이번 새 실행에 유지하지 않는다. 기존 사용량·ID·정산 이력과 D066 실패 원본은 보존한다. 이번 변경은 새 D067 조건이며 종료된 D066을 재개하지 않는다.

목표: 동일 OpenAPI Python client generator의 재귀 분해·관계·공개 수리를 실제 실행해 Claude 판단 기준과 비교한다. 새 4조건을 함께 시작해 각 조건 최대 동시 작업자 2명으로 실행한다. 기존 성공 기준선도 역사적 참고로 보존한다. 조건 병렬 실행과 공유 장부의 요청별 원자적 정산은 구분한다. 유료 실행과 실제 장부 이관은 root만 수행한다.

## 파일 소유권과 역할

- **budget**: `src/benchmark/budget.mjs`, 필요한 `src/benchmark/budget-acquire.mjs`, 신규 v3 예산 테스트, 명시적 v2→v3 이관 스크립트. `max_input_tokens:null`을 명시한 무상한 v3를 만들고 v1/v2의 제한 의미는 유지한다. 장부 ID·사용량·정산 수·마지막 정산을 유지한다. 모델 호출, 실제 장부 이관·초기화는 하지 않는다. 불확실 정산·계정 잔액·원자성 검사와 요청별 65,536 예약은 유지한다. 완료 후 정확한 인터페이스와 검증을 root/runner에 알린다.
- **runner**: `src/benchmark/adaptive-dag-runner.mjs`, `scripts/adaptive-dag-comparison.mjs`, 새 `benchmarks/e2e-swe/manifests/d067-adaptive.json`, 관련 runner 테스트. D066/v1은 그대로 재현 가능하게 두고 v2에서 조건별 토큰 상한 null·조건 병렬 4를 지원한다. 새 실행은 모두 terminal이 될 때까지 수집하고 공유 장부 잠금을 정상적인 대기로 처리한다. 실제 중첩·장부 대기 시간과 조건별 결과를 기록한다. 원시 기록·후보·장부 변경/유료 실행 금지. 공통 D066 catalog 바이트를 안전하게 재사용할 수 있는지 먼저 보고한다.
- **review**: 새 문서·한도 해제·이관·병렬 실행의 독립 검토. 먼저 source와 영향 범위를 읽고 중요한 반례만 제안한다. 수정은 자신의 `benchmark-runs/d067-review/` 새 증거만 허용한다. 생산 소스·원장·모델·숨김 검사 실행/열람 금지. 의미적 결함과 미측정 범위를 root에 알린다.
- **skills**: 기존 단일 스킬 담당 역할. `docs/agents/D067_SKILLS.md`, `docs/skills/MAINTENANCE.md`와 기존 스킬 참고 문서만 소유한다. 최신 사용자 승인으로 바뀐 한도와 과거 기록 보존·동시 장부·실행/정산 경계를 적용한다. 실제 문제 없이 새 스킬이나 helper를 늘리지 않는다. 전역 설치·유료 호출·생산 코드 변경 금지.
- **root**: 기술·결정·프로토콜·STATE·검증 기록, 통합 검사, 장부 이관, 한 번의 새 병렬 cohort, 독립 제품 채점, 별도 Opus 모니터와 최종 비용·시간 비교. 원본 Personal OS/Vault·기존 컨테이너·과거 후보를 보존한다.

## 공통 실행 경계

검토 중 소유권 보완: runner는 `src/benchmark/dag-runner.mjs`의 v3 명시 무상한 preflight 처리만 함께 수정한다. root는 `src/dashboard/metrics.mjs`, `dashboard/app.js`, 관련 projection 검사에서 무상한과 미확인 표기를 구분한다. 이 보완은 catalog 생성 질문·작업자 계약을 변경하지 않는다.

원문/요구사항·질문·선택지·작업자 모델/effort·공개 검사 조건은 이번에 임의 개선하지 않는다. 상한 해제의 결과를 먼저 관찰한다. 서비스의 요청 크기·모델 문맥 한도, 작업자 최대 30, 구현 동시성 2/조건, 재귀 깊이, 공개 수리 횟수, 불확실 결과의 비재전송 경계는 토큰 지출 상한과 다르다. 필요한 구조 제한 변경은 실제 차단 근거를 보고 별도 기록한다. 예산·잔여 무상한은 JSON null로 기록하며 0/Infinity/큰 가짜 숫자로 표시하지 않는다.

조건 병렬 때문에 공급자·CPU 부하가 공유된다. 새 동시 4조건 내 비교와 D066 순차 실행의 역사적 비교를 구분한다. provider receipt 성공, 완성 후보의 공개 85개 검사, 독립 63개 검사는 별도 근거다. 실패 시도시간은 완료 속도 향상이 아니다. 숨김 실패 세부내용을 수리로 넘기지 않는다. 역할별 현재 상태·검증·인계 문서를 남기고 문맥 한계 전에 후임에게 읽을 정본을 제시한다.
