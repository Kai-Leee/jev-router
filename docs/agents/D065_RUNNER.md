## Revision, environment and containment evidence

The filesystem runtime creates `runtime/` below the run directory, materializes immutable predecessors, runs each attempt in staging, checks declared scopes and publishes only verified output revisions. The runner passes `runtime.record` directly to the workflow so publication occurs before consumer release. Candidate output ownership is disjoint; paths are never silently merged between competing writers. Runtime check evidence is bound to the exact input/output artifact revision vector and pinned checker/fixture sources.

Every check creates a fresh container with the exact immutable image ID, platform `linux/amd64`, read-only root, network `none`, no additional capabilities, and read-only candidate/checker/binding mounts. Its executable `/tmp` matches the public environment's `/tmp:rw,exec,size=2g`, allowing isolated installed console scripts to execute. CPU/memory/process limits remain fixed controller containment. V2 candidate binding invokes the actual offline installer and installed generator via the public checker; it does not substitute authored controls for candidate output.

One actual preflight container records Python and dependency versions. Runtime boundaries inspect the exact immutable image ID and record inspection time, with versions explicitly labeled `preflight_probe_of_identical_immutable_image`. This preserves image identity without launching an extra dependency inventory container at every scope/check/publish boundary. Candidate-local installation is separately observed by the public checks. No host site-packages or mutable image tag enters a candidate container.

Environment probes and candidate checks share named create/start/remove lifecycle handling. The assigned name is durably recorded before creation, raw check output is saved before parsing, and removal is attempted even after a controller exception. Unconfirmed cleanup overrides an earlier known failure and returns an uncertain outcome. A parsed check report that marks an inner subprocess outcome uncertain raises `DAG_CHECK_REPORT_UNCERTAIN` before generic report-integrity rejection, even when the outer Docker process exited normally and removal succeeded. Runtime journals marked uncertain or invalid also prevent the final runner result from claiming completion. The standalone CLI catch preserves recognized uncertainty in both its status and `outcome_uncertain` field, including preflight/control exceptions.
