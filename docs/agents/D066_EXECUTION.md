## Implemented interface

```js
await runAdaptiveDagExecution({
  plan, artifactBindings, planning, run_id, runDirectory,
  checkerRoot, checkerFiles, environment, probeEnvironment,
  executeTask, checkTask, decideRepair, maxRepairRounds, record,
  testRequirements, // optional exact public test ID -> requirement ID list
});
```

`plan` is a validated artifact-dag/v1 plan whose implementation nodes are actual recursively chosen
multi-file leaves. Artifact bindings use the D065 runtime's explicit relative paths. Artifact producer
edges determine execution dependencies; no fixed sixteen-file grouping is imported. The planner and
runner supply this fresh plan/catalog and the same bounds for all comparison arms.

The runner supplies existing callback shapes: `executeTask(task,{attempt_id,stageDirectory,
input_artifact_revisions,...})`, `checkTask(check,{candidateDirectory,pinnedDirectory,environment,
artifact_revisions,...})`, and actual environment probing. Execution adds `operation` as implementation
or repair; `round_index`; `original_task_id`; and `repair_context` containing the selected action, public
failure reports, failed tasks, selected and invalidated tasks, and previous artifact revisions.
Carry-forward copies are recorded as `carry_forward` and do not invoke a model callback. `planning`
preserves the original source/catalog-bound planner result for `chooseAdaptiveRepair`.

Every round has a fresh directory, graph revision and D065 runtime journal. Previously generated bytes
are preserved in immutable round snapshots. Known failed local readiness may supply staged output for
repair, but never releases its consumers in that round. Transport-uncertain work stops the condition;
it is never automatically replayed in another round.

All required public suites run after a complete candidate even when an earlier suite returns a known
failure. A controller aggregate check runs each original integration check through the D065 runtime,
preserving its durable begin record, checker/environment pin audit and full revision-vector audit before
and after each invocation. The aggregate retains every original definition and report. On complete
success, the historical gate consumes the already bound child evidence without invoking a check twice;
on known failure, it rejects only after the complete suite set has been collected. Actual invocation
spans are `adaptive_public_check_started/completed`; `adaptive_public_evidence_reused` explicitly marks
cached gate validation. An uncertain process, invalid report or cleanup issue stops collection and
cannot trigger repair. The additive runner validates candidate-v2 public reports, including known
setup and partial-case failure; execution preserves executed/skipped/unexecuted distinctions as given.

`decideRepair(request,{stage:'repair',round_index})` wraps
`chooseAdaptiveRepair({source,...request,decide,record})`. Request fields are `planning`, `failure`,
`candidates`, and `limits:{max_repair_attempts,repair_attempts_used}`. The result is an exact offered
`{status:'selected',candidate_id,candidate,...}` or a stopped/uncertain result. Concrete actions are stop,
repair owners in the public/local failure scope, repair those owners plus downstream consumers, or
repair all leaves; identical scopes are removed. Requirement ownership constructs offered scopes and
does not prove root cause. Unexecuted public case IDs remain unexecuted in all evidence.

Root approved owners-only as a distinct action. No selected scope is silently expanded. Nonselected
consumers retain their bytes, receive fresh producer inputs, and rerun local plus complete integration
checks under the new vector. `round.operations` records the prior build inputs, prior validation inputs
and current input revisions. Repeated carries retain the original build-input provenance; this is
revalidation of carried bytes, not consumer regeneration. Selecting the consumer scope invokes actual
workers. Previously unbuilt leaves perform their first implementation even if within the selected
consumer scope, while previously attempted selected leaves perform repair. Root fixed `maxRepairRounds`
at 2 in every arm; no uncertain attempt can enter another round.

The result schema is `adaptive-dag-execution/v1`, with `status`, `outcome_uncertain`, `rounds`,
`repair_actions`, `repair_rounds_used`, `operations:{implementation,repair,carry_forward}`,
`candidate_path`, `artifact_revisions`, `public_evidence`, and durable journal paths. Each round retains
its plan, workflow, export, local/public evidence, operations, journal state and fatal error if present.
The failure packet includes source/catalog hashes when supplied, graph/run/attempt identities, runtime
binding/environment identity, exact public/local evidence, artifact revisions and undispatched tasks.
Independent grading remains root-owned and cannot enter repair context.

## Persistence and verification boundary

The controller exclusively creates `adaptive-execution` under the caller's fresh run directory. An
existing directory blocks replay, including after restart or a partially written operation. The
condition journal is hash chained and fsynced before round/repair side effects; each D065 round also
has its own durable worker/check journal. Completed earlier snapshots stay read-only and their exact
manifests are checked again before copying. Failed readiness can provide a scope-audited repair seed
but never publishes artifacts or releases consumers. Path audits and file modes are not an OS sandbox;
the runner supplies restricted worker transport and contained Docker checking.

Focused command: `node --test test/adaptive-dag-execution.test.mjs`. Latest completed run: 7/7 passing
(five top-level cases, including two worker/check uncertainty subcases). These local tests write real
multi-file artifacts and launch the pinned Node checker as a subprocess. They demonstrate dependency
release, all-seven known-failure collection, actual selected repair and downstream rebuild, carried
artifact rechecking, retained prior bytes, distinct unbuilt versus repair work, owners-only mismatch
detection under fresh inputs, exact selected scope, bounded repair and durable no-replay. They do not
establish product correctness, Docker containment, paid-provider integration or comparison speedups.

Runner owner reports its 5/5 focused integration passing with the actual planner/execution/runtime and
injected provider/Docker processes, including 14 public invocations across a selected repair. That is
local integration evidence, not live-provider or contained-product evidence. Independent reviewer fault
review and root's final source/protocol freeze remain pending. Historical D065 source, candidates and
