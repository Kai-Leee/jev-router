# Jev USD 1 예산의 호출 전 통제 가능성

확인일: 2026-10-09. D-020의 현재 실험 총예산 USD 1, 임의 호출 횟수 제한 없음에 대한 조사다. 공식 공개 문서만 읽었다. 이 조사 에이전트는 인증 API·계정·키·모델을 호출하지 않았고, 설치나 코드 변경을 하지 않았다. 계정 잔액은 이 문서에 기록하지 않는다.

## 판정

**공식 context 상한을 이용한 보수적 USD 환산 예산은 설계할 수 있다. 현재 공개 계약만으로 실제 계정 청구액의 USD 1 절대 상한이 보장됐다고 할 수는 없다.**

두 가지를 구분해야 한다.

| 통제 대상 | 현재 근거와 한계 |
| --- | --- |
| 실제 역사적 구매원가 / 계정 청구액 | 요청별 USD가 제공되지 않는다. 토큰의 구매 단가와 크레딧 가치도 계정마다 다를 수 있으므로 미확인이다. |
| 현재 공개 단가로 평가한 사용량 | USD 0.600 / 1M balance tokens라는 정책을 명시하면 계산할 수 있다. 이 값은 이번 조사에서 확인한 일회성 토큰팩 중 가장 높은 단가다. |
| 호출 전 다음 요청의 예약액 | Jev 1.13의 전체 context를 65,536 tokens로 보수적으로 잡아 예약할 수 있다. 다만 실제 과금 입력량이 이 상한을 넘지 않는다는 Jev AI의 명시적 계약은 확인되지 않았다. |
| 제공업체가 보장하는 키별 USD 차단 | 검토한 공개 문서에서 설정 방법 또는 API를 찾지 못했다. 비공개 계정 UI에 기능이 없다는 뜻은 아니다. |

## 확인한 공식 사실

Jev AI는 API에서 유료 입력 토큰을 우선 사용하고 부족하면 요청 전체를 크레딧으로 처리한다. 두 잔액을 동시에 차감하지 않는다. Jev의 배수는 1×이고 출력은 무료다. `usage.cost`가 빠지는 이유는 선불 토큰·플랜·증정 크레딧에 공통 요청별 USD가 없기 때문이다. 누락을 0으로 처리할 수 없다. 차감량·과금 모드·잔여량은 응답 헤더로 제공된다. [Jev API 과금 문서](https://jev-ai.pro/docs#billing)

현재 일회성 가격표는 15M/$9, 75M/$39, 200M/$76, 600M/$170이다. 따라서 15M 팩의 단가는 $0.600/M, 75M 팩은 $0.520/M이다. 가장 큰 팩의 표시값 $0.283/M는 반올림값이다. 이것은 계정의 실제 구매 내역이나 소진 크레딧의 달러 가치를 증명하지 않는다. [Jev 가격표](https://jev-ai.pro/pricing)

TypeSafe 모델 문서는 **64k가 state와 모든 질문을 합친 요청 전체 context**이며, state와 가장 긴 질문을 합친 별도 한도는 32k라고 명시한다. state를 한 번 읽으므로 질문마다 64k를 곱하는 해석은 맞지 않는다. 문서의 `64k`를 65,536으로 잡는 것은 64,000보다 넉넉한 로컬 정책이지, 정확한 서버 숫자로 확인된 값은 아니다. [TypeSafe 모델 계약](https://docs.typesafe.ai/models)

Jev AI도 64k/request와 32k/state+longest-question을 안내한다. 그러나 이 가이드의 과금 설명인 크레딧당 1M 토큰은 최신 API 문서의 tokens-first 및 요청 단위 credit fallback과 충돌한다. **context에는 TypeSafe 원문, 과금에는 현재 Jev API 문서와 가격표를 우선한다.** [Jev 1.13 가이드](https://jev-ai.pro/model/jev-1.13)

## 사전 차단 기능 조사 결과

| 조사 항목 | 확인 결과 |
| --- | --- |
| 키/계정별 USD 예산 파라미터 | 공개 API 문서에서 확인하지 못함. `402`의 spending paused라는 설명만으로 사용자 설정 가능한 USD 한도를 추정하지 않음. |
| quote / dry-run / count_tokens | 공식 공개 검색과 API 문서에서 발견하지 못함. |
| 요청의 `max_cost`, `max_input_tokens`, tokens-only 옵션 | 검토한 요청 스키마에 없음. 임의 필드를 보내 한도를 걸 수 있다고 가정하지 않음. |
| 잔액 조회 | 공개 API 안내에 `GET /api/v1/credits`가 있다. 잔액 조회는 요청의 확정 견적이나 원자적 예약 기능을 뜻하지 않는다. |
| 입력 제한 | JSON 256,000 bytes와 질문 64개는 validator 한도다. bytes를 과금 tokens로 환산하는 증거가 아니다. |
| 초과 context의 무과금 거절 | Mercury에는 명시되어 있으나 Jev에 동일한 무과금 보장을 확인하지 못함. 다른 모델의 보장을 전용할 수 없음. |

근거: [Jev API reference](https://jev-ai.pro/docs), [공개 API 안내](https://jev-ai.pro/jev-api), [TypeSafe HTTP API](https://docs.typesafe.ai/api). 검색 미발견은 기능 부재 증명이 아니며, 인증된 계정 설정은 조사하지 않았다.

## 구현 가능한 환산 정책과 필요한 조건

다음은 공식 사실을 조합한 **설계 제안**이다. 제공업체가 발급한 견적이나 보증이 아니다.

```text
valuation_rate = 0.600 USD / 1,000,000 balance tokens
request_reservation = 65,536 × 1 × valuation_rate = 0.0393216 USD
budget_limit = 1.0000000 USD

allow dispatch only if:
  settled_valuation + unresolved_reservations + next_reservation <= budget_limit
```

소액 응답이 정산되면 예약액을 실제 토큰 환산액으로 교체한다. 다음 요청도 항상 같은 조건으로 검사하므로 호출 횟수 자체를 고정하지 않는다. 단순히 누적액이 $1에 도달한 뒤 중단하면 마지막 요청이 한도를 넘길 수 있어 사전 통제가 아니다. 정수 단위 또는 정확한 소수 계산을 사용하고, 누적 토큰 정책으로 구현하면 `floor(1,000,000 / 0.600) = 1,666,666` balance tokens가 한도다.

이 정책을 보수적이라 부르려면 아래 전제와 실패 처리가 필요하다.

1. 요청은 검증된 Jev 1.13의 일반 `/v1/systemone` 경로여야 한다. 별도 검색·도구 부가요금·다른 배수의 모델을 같은 예약액에 포함하지 않는다. 단일 질문은 분석을 단순하게 만들지만, 문서상 64k 자체는 전체 질문 합계 한도다.
2. 모델 별칭이 새 버전으로 이동하면 기존 context 전제가 유지되는지 재검토한다. 응답에서 버전 변경을 발견하는 것은 사후 검사이므로 완전한 사전 보장이 아니다. 버전 고정 여부는 실행 담당자가 기존 `jev-latest` 요구와 함께 결정한다. [TypeSafe 별칭 규칙](https://docs.typesafe.ai/models)
3. 성공 요청의 과금 입력량이 전체 context 이내이며, 게이트웨이 내부 작업이 별도 입력량으로 합산되지 않는다는 전제가 필요하다. 공개 문서에서 이를 과금 상한 문장으로 확정하지 못했다. 실제 사용량이 예약보다 커지면 사후 중단해도 첫 초과를 되돌리지는 못한다.
4. 토큰 과금 모드를 유지하려면 충분한 paid-token 잔액이 필요하다. 잔액 GET 이후 다른 키·playground·프로세스가 소비하면 credits fallback이 생길 수 있다. 로컬 실험 락은 계정의 외부 소비를 잠그지 못하므로, 조회만으로 전 계정의 원자적 보장은 성립하지 않는다.
5. 실행 전 예약을 내구성 있게 기록하고 모든 실험 워커가 같은 원장을 사용한다. 프로세스 재시작·timeout·응답 유실로 결과가 불명확하면 예약을 해제하지 않는다. 이전 요청이 미확정인 채 자동 재전송하지 않는다. [Jev 오류 및 재시도](https://jev-ai.pro/docs#errors)
6. 정산 시 모드, 차감 토큰, 배수, 모델, 호출 식별자를 검증한다. credits 발생·필수 과금 필드 누락·불명확한 응답이면 다음 호출을 차단하고 `unknown` 상태로 둔다. raw usage와 실제 balance-token 차감량을 별도로 보관한다.

권장 표시는 **“Jev 사용량의 보수적 USD 환산 한도 $1”**이다. `actual_billed_usd`와 환산액을 다른 필드로 두고, 실제 USD가 확인되지 않으면 null을 유지한다. “실제 청구액 $1 절대 보장”으로 표시하려면 Jev AI가 제공하는 원자적 예산 차단 또는 최대 과금량 계약이 추가로 확인되어야 한다.

## 검증 범위와 다음 확인점

이번 결과는 공식 문서 비교 및 산술 검토다. 모델 실행, 실제 과금 측정, 초과 입력 테스트, 계정 한도 설정 검증을 수행하지 않았다. 구현 완료나 live hard cap 검증을 뜻하지 않는다.

남은 핵심 확인점은 하나다: **Jev AI에서 Jev 1.13 한 요청의 `X-Jev-Paid-Input-Tokens-Used`가 65,536 이하로 제한되며 초과 입력/내부 재시도로 이를 넘지 않는가?** 이 보장과 credits fallback 방지 수단이 확인되면, 공개 단가 환산 정책에 대한 사전 예약 근거가 더 강해진다. 현재는 조건부 정책으로 설명하고 문서로 보장되지 않은 부분을 숨기지 않는다.
