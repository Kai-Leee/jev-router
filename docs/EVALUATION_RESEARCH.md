# Jev Router 평가 방법 조사와 구현 제안

확인일: 2026-10-08 (Asia/Seoul). 상태: 공개 논문·공식 문서 조사 완료.
조사 당시 지표 계산기는 미구현이었다. 이후 D-012에서 [오프라인 평가 CLI](EVALUATION_USAGE.md)와
[구현 계약](EVALUATION_CONTRACT.md)을 추가했다. 아래 P0/P1/P2는 전체 계획이며 전부 구현됐다는 뜻은 아니다.
사용자 요청 [D-011]: 평가 지표를 구현하기 전에 기존 연구·실무에서 어떻게 평가하는지 조사한다.
이 문서의 적용안은 assistant 제안이며 지출 예산·품질 임계값을 확정하지 않는다.

## 1. 조사 결론

하나의 정확도나 절감률로 제품의 효과를 판단하기 어렵다. Jev Router에는 다음 평가를 구분해 적용한다.

1. **질문 준비:** 목표·제약·근거와 후보를 질문에 제대로 담았는가.
2. **판단:** 같은 입력에서 선택·분류·근거 판정·점수·확률이 적절한가.
3. **후속 작업:** 그 판단을 사용한 실제 작업이 성공했는가.
4. **전체 효율과 운영:** 질문 생성부터 결과 활용까지 시간·청구·실패·보류가 어떻게 바뀌었는가.

외부 연구가 사용하는 방법을 참고하는 제안이다. 외부의 성능 수치가 우리 프로젝트의 성능을
증명하지 않으며, API 모델 비교와 Claude/Codex 같은 모델+에이전트 실행환경 비교를 섞지 않는다.

이 비교는 공개 방법과 문서 기능의 확인이다. 실제 도구 설치·호스트 연결·동일 조건 벤치마크는 하지 않았다.
어떤 도구가 업계에서 가장 많이 쓰이는지에 대한 시장 점유율 조사는 아니다.

## 3. 판단 불가·확률·주관적 평가에서 확인한 점

- **답한 비율과 답한 건의 오답률을 함께 본다.** Selective classification은 일부 입력의 답을
  보류하며 coverage와 risk를 함께 다룬다. 이 관점을 적용하되 논문의 위험 보장 조건을
  Jev의 confidence에 자동 적용하지 않는다.
  [Selective Classification, 2017](https://arxiv.org/abs/1705.08500)
- **확률 평가와 보정 평가를 구분한다.** Brier score와 log loss는 확률 예측을 평가하지만
  보정만 측정하지는 않는다. reliability diagram과 함께 확인하고 보정 자료와 최종 평가 자료를
  분리한다. 낮은 Brier 하나로 confidence가 정확하게 보정됐다고 결론 내리지 않는다.
  [scikit-learn probability calibration](https://scikit-learn.org/stable/modules/calibration.html)
- **채점 모델도 오판한다.** MT-Bench 연구는 답변 순서를 바꾸었을 때 판단이 달라지는 위치 편향을
  조사했다. 비교 대상 이름을 가리고 순서를 교환하며, 사람이 검토한 사례와 채점 결과를 대조하는
  정책을 제안한다. Jev가 자기 답의 최종 정답 판정까지 맡게 하지 않는다.
  [LLM-as-a-Judge, §3 및 Appendix D](https://arxiv.org/html/2306.05685v4)
- **공급자 값의 의미를 보존한다.** Jev 문서는 `noul` 확률, `choice`/`score`의 확률 맵과 confidence,
  실제 모델·usage·청구 헤더를 제공한다. 확인한 문서에서 우리 작업 분포의 정답률 보정 성능은
  확인하지 못했다. 원래 confidence, 선택지 확률, 별도로 추정한 정답 확률을 서로 덮어쓰지 않는다.
  [Jev AI typed questions / billing / errors](https://jev-ai.pro/docs)

## 4. 먼저 구현할 지표 계약 / 제안 P-004

### 집계 단위와 공통 규칙

- `task_id`는 실제 작업, `trial_id`는 반복 실행, `decision_id`는 판단 지점,
  `request_id`는 HTTP 시도, `question_id`는 요청 안의 개별 질문이다.
- 질문이 여러 개인 요청의 청구를 질문별로 복제해서 합산하지 않는다. 비용은 request 기준으로
  한 번 기록한다. 질문별 배분을 추정하면 배분 규칙과 추정임을 별도로 표시한다.
- `N`은 평가 manifest에 미리 등록한 판단 사례 수, `L`은 그중 참조 답/판정 기준이 확정된 사례 수다.
  `A`는 유효한 실질 답변을 반환한 사례 수, `E`는 L 중 유효한 실질 답변을 채점한 사례 수다.
  abstained/실패/불명/미실행은 서로 다른 상태로 보존한다.
- 모든 비율은 분자·분모·단위·제외 사유를 함께 반환한다. 분모가 0이면 `null`과 사유를 반환한다.
  집계 대상에서 사라진 실패·미실행이 없어야 한다. 미채점은 오답이라고 기록하지 않는다.
- 아래 `P0/P1/P2`는 제안하는 구현 순서다. 실제 성능 측정 결과나 사용자 확정 임계값이 아니다.

### P0 — 공통 보고서

1. **유효 응답과 실행 상태:** HTTP를 시작한 요청 전체에 대해 completed/failed/unknown 건수,
   응답을 받은 요청 중 스키마 통과 건수. 질문 수준의 형식 통과도 별도로 기록한다.
   로컬 준비 실패와 manifest 미실행은 요청 실패와 나눠 표시한다.
2. **답변 coverage:** `A / N`. 채점 가능 coverage는 `E / L`로 별도 표시한다.
   **selective risk:** `오답 수 / E`; **판단 정확도:** `정답 수 / E`.
   **검증된 정답 산출률:** `정답 수 / L`은 보류·실패로 결과를 못 낸 경우까지 드러내는 보조 지표다.
   이것을 미채점 사례의 실제 오답률로 부르지 않는다. 참조 없는 비중 `(N-L)/N`도 표시한다.
3. **잘못된 자동 채택:** 알려진 필수 제약을 위반한 채택 수 / 제약 검사가 가능한 채택 수.
   자동 채택 자체의 비율은 전체 판단 수를 분모로 별도 보고한다. 메인의 채택은 정답 라벨이 아니다.
4. **작업 성공률:** 독립적인 최종 상태 검사에 통과한 trial 수 / 예정된 전체 trial 수.
   실패·시간 초과·미실행·아직 평가 못 함의 건수를 함께 제시한다. 검증기 오류는 에이전트의
   의미적 오답과 분리하고, 유효 검증을 받은 trial의 조건부 성공률도 함께 보고한다.
5. **시간:** 질문 생성 시작부터 메인이 사용할 결과 준비까지 `decision_e2e_ms`, HTTP
   `api_ms`, 전체 작업 `task_e2e_ms`를 구분한다. 각 분포에 n, p50, p95와 분위수 계산법을 저장한다.
   실패까지 걸린 시간은 성공 지연에 섞지 않고 별도 분포로 보고한다. timeout은 실제 완료시간이 아니다.
   병렬 구간의 시간을 더해 벽시계 시간으로 제시하지 않는다. 작은 표본의 p95는 안정성을 주장하지 않는다.
6. **비용:** 모든 질문 생성·판단·실행·재확인 시도의 실제 usage/청구를 합산한다.
   오프라인 평가용 judge 비용은 `evaluation_cost`, 실제 작업 수행비는 `operational_cost`로 분리한다.
   USD·Jev balance tokens·credits·CLI 사용량은 단위별로 기록하며 환산 근거 없이는 합치지 않는다.
   구독 CLI의 추가 청구를 알 수 없으면 무료/0달러라고 쓰지 않는다.
7. **성공당 비용:** 동일 cohort의 전체 운영 비용 / 성공한 trial 수.
   실패한 시도의 비용도 분자에 들어간다. 성공이 없거나 비용 누락이 있으면 완전한 지표는 `null`이다.
   누락 시 관측된 부분합과 비용 관측 건수 / 전체 비용 발생 가능 건수를 따로 보여준다.

### P1 — 판단 종류별 품질

| 판단 종류 | 제안 지표 | 필요한 기준 / 계산하지 않을 조건 |
|---|---|---|
| 단일 분류·근거 판정 | confusion matrix, 클래스별 precision/recall, macro-F1 | 고정 라벨 집합과 클래스별 support 필요. 보류를 숨기지 않도록 coverage 동반. 근거 부족은 반박과 별도 라벨 |
| 선택·다음 단계 | 허용 답 집합 포함률, 필수 제약 통과율, 후속 작업 성공 | 적절한 답이 여러 개면 하나의 정답 ID만 강제하지 않음. 선호가 모호하면 인간 루브릭·pairwise 평가 |
| 확률·예측 | Brier, log loss, reliability diagram | 명확한 사건/기간과 관측 라벨 또는 고정 클래스의 참조 답 필요. 단순 후보 선호 분포를 모델별 성공 확률로 채점하지 않음 |
| 순위 | 평가 가능한 쌍의 선호 일치율, graded relevance가 있으면 NDCG@k | 비교 불가·동률 유지. 참조 순위/관련도가 없으면 순위 품질은 미측정. 모델 confidence만으로 relevance를 만들지 않음 |
| 질문 생성 | 필수 사실·제약 보존율, 후보 적격률, 순서 변경·의미 보존 재표현에서 판단 일치율 | 필수 항목을 원문에서 미리 정함. 같은 원문 파생본을 독립 표본으로 세지 않음. 일관성은 정확성과 별개 |

분류 구현은 [scikit-learn F1 정의](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.f1_score.html)를
기준으로 독립 검산한다. macro-F1은 클래스별 F1을 동일 가중 평균하며 support·0 분모 정책을 기록한다.
순위는 [scikit-learn NDCG](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.ndcg_score.html)의
동률 처리와 gain convention을 확인해 고정한다. 부분 선호만 있으면 완전 순위로 임의 보충하지 않는다.

확률 계산 계약 제안:

- binary Brier = `mean((p-y)^2)`. multiclass Brier = `mean(sum_k((p_k-y_k)^2))`.
  각각 범위 [0,1], [0,2]인 convention이며 값의 크기를 그대로 서로 비교하지 않는다.
- log loss = `mean(-log(p_true))`. 참조 라벨 확률이 0이면 수학적으로 무한대다.
  JSON에서는 `null` + `infinite_loss`와 해당 건수를 보존하거나, 사전 명시한 clipping 규칙의
  별도 값을 보고한다. 조용히 확률을 바꾸지 않는다.
- 확률 합·허용 라벨·유한성 검사를 먼저 한다. 합 검사 허용오차는 구현 시 명시하며 실패값을
  자동 정규화해 정상 응답처럼 만들지 않는다. 보정용 입력 confidence의 의미도 고정한다.
- reliability bin의 경계·표본 수·평균 확률·실제 정답 비율을 기록한다.
  ECE 같은 요약치는 bin 방식과 표본 수에 민감하므로 초기에 단독 합격 기준으로 삼지 않는다.

### P1 — 모델 선택 효과

판단하는 모델(Jev/Claude/OpenAI 모델)과 실제 일을 수행하도록 선택되는 모델/CLI를 별도 필드로 둔다.
라우터가 출력한 모델 이름의 일치율보다, 선택된 실행자가 만든 결과의 품질을 우선 평가한다.

- 고정 모델 기준: 개발 자료에서 정해 고정한 실행자. 비교 모델별 고정 실행 결과도 보존한다.
- random/단순 규칙 기준: 허용 후보 집합 안에서 선택; 비용 예산·후보 비중을 맞춘 비교도 포함한다.
- 사후 Best Single: 평가 자료 전체 결과를 본 후 가장 나았던 단일 모델. 배포 정책과 구별한 참고값.
- 사후 Oracle: 사례별 관측된 후보 결과 중 가장 좋은 값. 품질 동률이면 알려진 비용으로 구분 가능.
  온라인 사용 가능한 라우터가 아니며, 반복 실행의 우연한 성공을 고른 효과가 있을 수 있다.
- 품질 regret = `mean(best_observed_quality_i - selected_quality_i)`.
  같은 후보 집합·루브릭으로 모든 필요한 결과가 관측된 사례에서만 계산하고 대상 수를 공개한다.
  선택한 실행자의 결과만 있는 운영 로그로 다른 후보가 나빴다고 추정하지 않는다.
- 비용 절감률 = `1 - total_cost_router / total_cost_baseline`.
  같은 작업군·통화에서 비용이 완전 관측되고 기준 비용이 양수일 때만 계산한다.
  품질 차이와 불확실성, 허용 품질 저하 여부를 함께 보고한다. 비용만 낮다고 라우팅이 우수한 것은 아니다.
- 비용–품질 Pareto 곡선을 먼저 사용한다. 품질·시간·비용을 임의 가중치의 하나의 점수로 합치지 않는다.

### P2 — 운영과 handoff

로드 밸런싱은 별도의 부하 실험으로 처리한다. [k6 built-in metrics](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)는
요청 실패, 지연, 미시작 iteration을 구분한다. 특히 `http_req_duration`은 초기 DNS/연결 시간을
포함하지 않으므로 이를 우리 `task_e2e_ms`로 대체할 수 없다.

적용 제안: 부하 도착률·동시 실행 수를 기록하고 처리량, queue 대기, p95/p99, 429/5xx/timeout,
미시작 요청, 실패 복구 후 결과를 비교한다. 고정 도착률과 동시 사용자 기반 부하를 구분한다.
후보에게 균등 분배했다는 사실만으로 품질이나 부하 분산의 적합성을 주장하지 않는다.
현재 실제 부하 실험은 수행하지 않는다.

handoff는 필수 사실/제약 보존, 원문 재조회, 후속 작업 성공, 복구 시간, 총 토큰을 비교한다.
기본 판단 실험과 분리하며 새 세션의 효과와 추가 근거를 다시 읽은 효과를 나눠 본다.

## 5. 비교 실험과 데이터 준비

첫 평가 자료는 실제 반복 판단·실패 사례를 중심으로 만든다. 합성 예제는 계산기와 형식 검증용으로
구분하며 사용자 효과 증거로 쓰지 않는다. 고정 표본 수나 유료 호출 횟수는 아직 정하지 않았다.

1. **판단 분리 실험:** 동일한 영어 질문·state·후보에 대해 Jev와 비교 판단자의 결과를 평가한다.
2. **질문 생성 효과:** 메인의 기존 직접 판단과, 정형 질문을 작성한 뒤 메인이 판단하는 조건을 비교한다.
3. **전체 흐름:** 같은 초기 작업 상태에서 직접 수행과 Jev를 포함한 자동 판단 흐름을 비교한다.
   후보 생성과 재확인의 시간·비용도 포함한다. 후보 고정 실험과 혼합하지 않는다.
4. **자동 호출 정책:** 호출한 경우뿐 아니라 생략·보류된 판단 지점을 기록한다. 사람이 필요성을
   라벨링한 부분집합에서 트리거 precision/recall을 검토할 수 있지만, 주 지표는 작업 품질과 총 비용이다.
5. **예외 자료:** 근거 부족, 적합 후보 없음, 모순된 제약, 후보 동률, 의미가 같은 질문/후보 순서 변경,
   확률·응답 오류, 429·연결 단절을 포함한다. 전송 장애는 우선 모의 환경으로 검증한다.

개발/보정/최종 평가를 분리한다. 같은 작업의 재표현·후속 판단·반복 실행은 동일 그룹으로 묶는다.
평가 결과를 보고 선택한 임계값의 점수를 다시 미사용 평가 성능으로 보고하지 않는다.
문항·근거·후보·질문 템플릿·grader·split manifest의 버전/해시를 저장한다.
참조 정답·grader 전용 기준·평가용 후보별 실제 결과 표를 질문 생성기나 라우터 입력으로 보내지 않는다.
후보 설명에 쓸 과거 성능은 개발 자료에서 얻은 것임을 표시하고, 평가 대상의 사후 결과와 분리한다.
모든 비교는 작업군별 값과 사전 고정한 전체 가중치를 함께 기록해 큰 작업군이 작은 작업군을 숨기지 않게 한다.

API 비교에는 실제 모델 ID·응답 버전·설정을, CLI 비교에는 추가로 CLI 버전·실행 도구·권한·환경·
reasoning 설정·자원 한도를 기록한다. `Claude`, `Codex`라는 제품명만으로 실행 조건을 고정했다고 하지 않는다.
재실행은 정상적으로 계획한 별도 trial이며 결과 불명 POST의 재전송과 구분한다.

짝을 맞춘 사례별 차이를 보고, 신뢰구간은 같은 원본 작업 그룹 단위의 재표집 등 상관을 반영한다.
단일 비율에는 Wilson 구간을 검토하고, 반복 시도 전체를 독립 문항으로 부풀리지 않는다.
반복 신뢰성은 trial별 성공률과 모두 성공한 작업의 비율을 구분한다. 관측된 반복 결과 없이
평균 성공률을 거듭제곱해 실측 안정성이라고 쓰지 않는다.

## 6. 채점 원칙과 도구 선택 제안

코드·라벨·파일 상태로 확인할 수 있는 것은 결정론적으로 채점한다. 자유로운 다음 단계나
접근법 비교는 명시적 루브릭과 사람이 검토한 사례로 채점자를 점검한다. 채점자 간 불일치를
보존하고 최종 판단 근거를 기록한다. 숨겨진 사고 과정은 필요하지 않고 관측 가능한 입출력·행동을 남긴다.

현재 Node CLI가 있으므로 우선 로컬 JSONL 기록과 순수 지표 계산기를 얇게 추가하는 구성을 제안한다.
외부 플랫폼 가입·도입을 첫 평가의 전제로 두지 않는다. Promptfoo는 프롬프트/형식 회귀,
Inspect는 반복 실험·통계 집계, LangSmith는 운영 trace와 평가 연결의 후보로 둔다.
이 중 어느 것도 설치하거나 Jev 연결 호환성을 시험하지 않았다.

계산기 구현 시 필요한 검증 사례: 전부 보류, 응답 실패, 라벨 없음, 한 클래스만 존재,
0 확률, 잘못된 확률 합, 순위 동률/관련도 없음, 청구 누락, 성공 0건, 다중 질문 단일 청구,
반복 trial 그룹, 같은 자료를 두 번 집계한 경우. 손계산 가능한 fixture와 독립 구현의 결과를 대조한다.

## 7. 조사 당시 구현에서 확인한 차이 / 이력

확인 방법: [client.mjs](../src/client.mjs), [package.json](../package.json)의 직접 읽기.

- 있음: 응답 형식·확률 원소 범위 검사, 실제 모델, usage, 청구 헤더, 성공 응답의 HTTP 소요 시간.
- 아직 없음: 확률 합 검사, 질문 생성/전체 작업 span, 실패 시도의 완전한 시간·비용 기록,
  참조 답·독립 grader, 고정 평가 manifest, 결과 파일/지표 계산기.
- 단일 HTTP `durationMs`는 질문 생성·메인 해석·최종 작업을 포함하지 않는다.
- 기존 연결 테스트 통과는 판단 품질이나 절감 효과 측정이 아니다. 이번 조사에서 이를 새로 측정하지 않았다.

구현 제안 순서: 사례·결과 스키마 → P0 집계와 누락 처리 → P1 판단별 채점 → 고정 입력 비교 →
자동 호출을 포함한 작업 평가 → P2 handoff/부하 실험. 평가 코드는 아직 추가하지 않았다.
이 문단은 조사 시점의 상태다. 이후 구현 범위와 남은 항목은 위 구현 계약/사용 문서와
[검증 기록](../VERIFICATION.md)을 따른다.
