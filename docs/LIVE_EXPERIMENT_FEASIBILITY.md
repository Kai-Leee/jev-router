# Opus 5.5 + Jev 실제 구현 평가 가능성

후속 상태: 사용자가 D-014로 두 과제 병행 진행을 요청했다. 클론·실행기·평가기와 실제 Docker
무과금 검증은 [최신 벤치마크 기록](../benchmarks/README.md)을 따른다. 아래는 그 구현 전 조사 기록이다.

확인일: 2026-10-08 (Asia/Seoul). 요청 근거: D-013. 상태: 조사와 연결 준비 상태 확인 완료,
실험 설계 제안 P-005. 실제 구현 실험·모델 성능 측정은 아직 하지 않았다.

## 결론

가능하다. 목표·명세만으로 소프트웨어를 만드는 공개 평가 과제와 Claude Code용 평가 실행기가
이미 존재한다. 따라서 기존 방법이 없다고 보고 Personal OS 재구현을 바로 시작하지 않는다.
공개 과제로 연결을 확인한 뒤, 사용자 업무와의 적합성은 Personal OS의 별도 목표·명세 과제로
평가하는 구성을 제안한다. 이 순서는 실험 준비 순서이며 구현 에이전트에게 줄 task 목록이 아니다.

Jev는 구조화 판단 모델이다. 질문·후보 생성, 코드 작성과 도구 실행까지 Jev가 수행하는 구성이
아니라 **Opus가 준비·구현하고 Jev가 명시적 분기를 선택하는 구성**이다. Opus 내부의 모든 판단을
없앴다는 주장은 검증할 수 없다. 외부로 드러난 결정 지점과 실행의 연결을 측정해야 한다.

## 기존 방법: 과제와 실행기를 구별

| 방법 | 이번 요청에 맞는 점 | 남는 차이 / 검증 수준 |
| --- | --- | --- |
| [E2E-SWE](https://github.com/facebookresearch/E2E-SWE) | 자연어 명세 + 빈 작업 공간 → 설치 가능한 저장소. 새 환경 설치 후 비공개 테스트로 평가 | 공식 README·공개 과제 확인. 기본 예시는 mini-swe-agent이며 Claude/Jev 결합은 추가 연결 필요. 완성 앱 UX를 보장하지 않음 |
| [Harbor](https://docs.harborframework.com/) | 과제·격리 환경·에이전트·평가기를 분리하여 실행 | 실험 기반이며 Jev 판단 정책 자체는 제공하지 않음. 로컬 설치/실행 미검증 |
| [Inspect SWE](https://meridianlabs-ai.github.io/inspect_swe/reference/) | Claude Code solver, MCP와 host-side bridged tools 제공 | Jev를 별도 도구로 연결할 수 있는 문서상 확장점. 우리 조합 E2E는 미검증 |
| Personal OS 자체 과제 | 실제 사용자의 목표·Markdown 호환·상태 복구·화면 행동 평가 가능 | 요구사항 정제와 독립 평가기 필요. 기존 앱이 모든 기능을 완료했다는 전제는 부적절 |

[Inspect Harbor](https://meridianlabs-ai.github.io/inspect_harbor/agents.html)는 Harbor 과제에
Inspect SWE의 Claude Code solver를 사용하는 예제를 제공한다. 추천 연결 후보는
`Harbor 형식 과제 → Inspect Harbor/SWE → Claude Code + host-side Jev 도구`다.
현재 E2E-SWE의 separate verifier/네트워크 조건과 이 조합의 호환성은 실제 실행으로 확인해야 한다.
문서상 연결점의 존재를 turnkey 지원으로 표현하지 않는다.

E2E-SWE README는 지정 Harbor 버전의 separate verifier 경로에서 테스트가 업로드되지 않아
모든 과제가 0점이 되는 문제와 수정 방법을 알린다. 이를 실행해서 재현한 것은 아니다.
실험 전 빈 결과가 실패하는 음성 대조와, 가능한 경우 공개 정답 또는 평가자가 만든 정상
fixture가 통과하는 양성 대조를 실행한다. 테스트 파일 존재·발견 건수·skip·실행 실패도 확인한다.
평가기 오류를 모델 실패율에 합치지 않는다. 참고 해법은 구현 에이전트에 제공하지 않는다.

추가 벤치마크 비교와 실제 공개 자산 확인은 [담당 조사 기록](agents/live-benchmark-STATUS.md)에 둔다.

## Opus / Jev / 실행기의 책임

[공식 모델 문서](https://platform.claude.com/docs/en/models/opus-5-5/overview)에서
`claude-opus-5-5`를 확인했다. 실제 계정 접근은 모델 호출로 검증하지 않았다.

```text
사용자 목표 + 관찰 가능한 수용 기준 + 제약 (구현 단계 없음)
    ↓
Opus: 상태·근거 수집, 필요한 판단 질문과 후보를 영어로 구성
    ↓
서버 도구: 요청 검증 → Jev → 결과/사용량/판단 ID 기록
    ↓
Opus: 선택된 후보에 맞춰 코드·테스트·다음 제안을 생성
    ↓
독립 실행기: 결정과 행동 연결 확인, 도구 실행, 결과 기록
    ↺ 새 근거에 따른 다음 분기
    ↓
독립 평가기: 종료 후 별도 환경에서 기능·제약·복구 검증
```

- Jev: 접근법 선택, 다음 작업 후보, 실패 후 재계획, 주장에 대한 근거 판정, 종료 준비 여부 등
  명시적 판단. 후보에 정보 부족·적합한 후보 없음 등을 포함하고 근거 없는 선택을 강제하지 않는다.
- Opus: 목표 이해, 후보/질문 생성, 선택된 접근의 구현과 도구 입력 생성. 질문이 편향되거나
  좋은 후보가 없으면 Jev만으로 회복되지 않으므로 후보 품질도 기록한다.
- 결정론적 실행기: 입력 한도, 상태 버전, 허용된 도구/경로, 결정과 실제 실행의 연결을 확인한다.
  Jev의 판단은 사용자의 권한 부여나 개인정보·실제 앱 수정 허가를 대체하지 않는다.
- 평가기: Jev의 종료 판단이나 Opus의 완료 보고와 별도로 성공 여부를 판정한다.

첫 비교에서는 모델 선택 변수를 줄이기 위해 구현자는 Opus로 고정하고 Jev의 판단 효과를 본다.
다른 실행자 선택·부하 분산은 후속 비교다. 이는 장기 제품 범위 D-001을 축소하는 결정이 아니다.

## 자동 판단을 실제 행동에 연결하는 방법 / 미구현 제안

프롬프트에 “Jev를 사용하라”만 적으면 호출 누락과 무시를 구별하기 어렵다.
[Claude Code PreToolUse](https://code.claude.com/docs/en/hooks)는 도구 실행 전 차단을 지원한다.
이를 외부 controller와 연결해 주요 분기에 최신 Jev 결과가 없으면 후속 실행을 보류하는 방식을 제안한다.

권장 초기 분기는 새 접근 선택, 선택한 범위의 완료, 실패 후 재계획, 최종 종료 제안이다.
작업 단위와 순서는 Opus가 스스로 만든다. 사람이 파일별 task나 정답 계획을 제공하지 않는다.
매 읽기·매 문자 편집마다 유료 판단을 추가하는 설계는 제안하지 않는다.

`decision_id`, 현재 근거/후보 버전, 선택 후보, 적용 범위, 뒤따른 tool/action ID를 연결한다.
새 근거로 기존 결정이 무효해지면 다시 분기를 열고, 오랜 결정을 무제한 실행 허가로 재사용하지 않는다.
결과 원장과 gate 설정은 에이전트의 쓰기 가능한 코드 영역 밖에 둔다. 일반 Bash나 다른 도구로
우회할 수 있는 권한이 남았다면 '결정 강제'가 아니라 advisory 실험으로 표시한다.
이 제어는 행동의 의미가 후보와 완전히 같다는 보증이 아니다. 사후 trace 검토와 제약 테스트가 필요하다.

[Opus 5.5 변경 문서](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5)는
`tool_choice`의 강제 `any`/특정 `tool` 요청을 지원하지 않는다고 명시한다.
API의 강제 tool choice만으로 이 흐름을 만들지 않는다. `strict` schema는 형식 검증이지 호출 강제가 아니다.

판단 불가, malformed 응답, 통신 실패를 분리한다. 판단 불가는 필요한 근거를 추가할 수 있는
정해진 경로로 보내고, 결과 불확실한 POST는 재전송하지 않는다. 실패 때 Opus가 조용히 대신
선택하거나 다른 모델로 바꾸면 별도 조건으로 기록한다. 끝없는 재질문은 예산/시간으로 종료한다.

## 목표·명세만 전달하는 Personal OS 과제

[원문 근거와 정제 제안](agents/personal-os-spec-STATUS.md)을 먼저 확인한다.
현재 문서의 구현 상태는 기능별로 다르며, 오래된 미완료 문구보다 최신 확인 범위를 대조해야 한다.

전달할 내용은 제품 목표, 사용자 행동과 기대 결과, Markdown 외부 계약, 데이터 보존·복구 규칙,
종료 수용 기준, 합성 입력이다. 기존 앱 소스·테스트 정답·Task Board·수정 이력·내부 함수명·
개인 Vault·운영 포트·실제 사용자 기록은 전달하지 않는다. 영어 명세를 기본으로 하되 원문 계약의
필드·날짜 의미·식별자 의미를 바꾸지 않는다.

Today/Week/Calendar/Backlog, 작업 완료와 일정 변경, Focus/Time Log, Markdown 재조회·복구
같은 관찰 가능한 결과를 평가 대상으로 구성할 수 있다. 범위는 아직 최종 확정하지 않았다.
Linux 웹/파일 평가와 macOS native 앱의 설치·재시작·Focus 복구는 별도 증거층이다.
전자를 통과했다고 데스크톱 재구현 완료로 보고하지 않는다.

에이전트가 자율적으로 계획을 만드는 것은 허용한다. 평가자는 무엇이 성공인지만 사전에 고정한다.
핵심 요구를 숨긴 뒤 실패시키지 않되 평가 구현·구체 데이터·정답 해법은 에이전트에 노출하지 않는다.

## 비교와 평가 지표 / 제안

| 조건 | 목표·명세 | 판단 역할 | 확인할 효과 |
| --- | --- | --- | --- |
| A: Opus 기본 | 동일 | Opus | 기존 에이전트 기준선 |
| B: Opus 구조화 | 동일 | 같은 질문/후보 계약을 Opus가 판단 | 구조화 질문과 controller 자체의 효과 |
| C: Opus + Jev | 동일 | Opus가 질문 구성, Jev가 선택 | B 대비 판단자 교체, A 대비 전체 방식 |

처음에는 A/C로 연결을 점검할 수 있으나 이를 Jev 판단자의 인과적 우위로 주장하지 않는다.
질문 형식·후보 생성 자체의 효과를 구별하려면 B가 필요하다. 비용 상한·모델 effort·실행 도구·
초기 파일·종료 기준·반복 횟수를 사전 기록한다. 실패·시간 초과·예산 종료도 전체 run 분모에 포함한다.
순서를 섞고 독립 초기 상태를 사용하며, 한 번의 앱 재구현으로 일반 우열을 주장하지 않는다.

- 최종 성공: 통과한 필수 수용 기준 수 / 적용 가능한 필수 기준 수. 전체 통과 run 수 / 시작한 run 수.
  미검증·실행기 오류·제품 실패를 따로 남긴다.
- 수행 비용: 질문 준비·Opus 구현·Jev 판단·복구·실패를 모두 포함한다. 평가용 judge 비용은 분리한다.
  벽시계 시간과 각 공급자의 입력/출력/cache 사용량을 보존하고, 토큰 수만으로 금액 우위를 말하지 않는다.
- 판단 준수: 유효 Jev 결과와 연결된 결정 지점 수 / gate가 요구한 결정 지점 수.
  실제 행동과 선택의 일치, 우회, 무시, 보류, 오래된 결정 재사용을 별도 기록한다.
- 제품 품질: 누락 요구, 잘못된 완료 보고, 데이터 손상, 복구 실패, 독립 UI 검증 결과.
- 재작업/사람 개입: 원인별 발생 건수와 소요 시간. 필요한 사용자 답변과 evaluator의 해법 개입을 분리한다.

기존 오프라인 평가기는 기록을 계산할 수 있으나 이 trace의 자동 수집·변환기는 아직 없다.
E2E 결과/판단 원시 기록을 저장하고 실제 계약에 맞는 집계 레코드로 변환하는 연결이 필요하다.
[Jev 문서](https://jev-ai.pro/docs#errors)상 USD 비용이 없는 경우 토큰/credit 청구 단위를 보존하고
USD는 `null`로 둔다. Claude CLI의 `--max-budget-usd`가 외부 Jev 호출까지 제한한다고 가정하지 않는다.

## 현재 로컬 준비 상태와 재현 명령

실행 위치: `/Users/lee/workspace/plugins/jev-router`.

- `claude --version` → `2.1.280 (Claude Code)`.
- `claude --help` → `--model`, `--mcp-config`, `--strict-mcp-config`, `--max-budget-usd` 지원 확인.
- `claude auth status --json` → exit 1, `loggedIn:false`, `authMethod:none`.
  stdout은 JSON 파싱 후 위 비밀 없는 필드만 출력했다. 현재 실행 환경 결과이며 계정 자체의 이용 권한을 단정하지 않는다.
- `npm run --silent config` → 지정 Jev URL, `jev-latest`, 키 설정됨, 기본 비밀 파일
  `/Users/lee/workspace/.env` 확인. 키 값과 인증 헤더는 출력하지 않았다.
- `npm run --silent models` → 제한 네트워크 환경에서는 `TRANSPORT_ERROR`.
  네트워크 접근 허용 후 같은 **GET** 재실행은 exit 0, 목적지
  `https://jev-ai.pro/api/v1/models`, HTTP 200, 응답 목록에 `jev-latest` 확인.
  GET 성공은 유료 추론 성공의 증거가 아니다. POST는 실행하지 않았다.
- `command -v docker` → Docker CLI 있음. `docker info --format '{{.ServerVersion}}'`는
  처음 소켓 permission denied, 읽기 권한 허용 후에도 daemon 연결 실패. 엔진은 시작하지 않았다.
- `command -v harbor`, `command -v inspect` → 현재 PATH에서 찾지 못함.
  모든 Python 가상 환경에 패키지가 없다는 전수 확인은 아니다.

기존 Jev MCP는 macOS ARM64 바이너리다. Linux container 안에 현재 경로를 그대로 넣으면 안 된다.
host-side bridge로 기존 서버/직접 클라이언트를 호출하거나 검증한 Linux 실행물을 준비해야 한다.
Jev 키는 서버 측에 두고 agent의 작업 디렉터리나 브라우저에 복사하지 않는다.

Inspect 경로에서는 CLI 로그인과 별도로 호스트의 Anthropic provider 인증이 필요할 수 있다.
설치된 CLI만으로 Opus 접근 성공을 주장하지 않는다. 모델 식별 문자열만 바꾸는 `model_config`와
실제 served model을 구분하고, 실제 요청/응답의 모델을 기록한다. 기본 helper/subagent 모델과
재시도 설정도 명시해 'Opus + Jev' 외 모델이 조용히 섞이지 않게 확인해야 한다.

## 남은 일과 실행 경계

실험용 인증/컨테이너 환경, 버전 고정, Jev gateway와 행동 gate, 원시 기록 수집기, 독립 평가기,
시간·금액·Jev 호출 상한이 남았다. 이는 추가 구현이 필요한 구체 항목이며 이미 완성된 기능이 아니다.
실행 예산 O-003은 미정이다. 이번 조사에서 승인 대기 도구는 없고 유료 실행을 시작하지 않았다.

부수 효과: 이 저장소의 조사/역할/결정/상태 문서와 OS 임시 handoff 기록만 로컬 변경.
패키지 설치, 컨테이너 생성, Personal OS 수정, 유료 추론, commit/push는 하지 않았다.
